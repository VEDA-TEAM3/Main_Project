# Control-server `zone` 최적화 보고서

- 작성일: 2026-07-29
- 대상: `control-server/src/zone/SpatialZoneMapper`
- 기능 기준: 수정 전 프로덕션 구현
- 적용 방식: 4구역 고정 비교, 64구역 이상 정적 좌표 결정표, 예외 입력 선형 폴백

## 1. 결론

`SpatialZoneMapper`의 핵심 계약인 선언 순서 first-match, 경계 포함, 미배정 `zoneId=-1`,
미배정 로그 순서를 유지하면서 구역 수에 따라 다른 실행 경로를 적용했다.

```text
정확히 4구역
  → 프레임당 한 번만 구역 수 확인
  → 네 구역을 선언 순서대로 고정 비교

0~63구역(4구역 제외)
  → 기존 선형 비교 유지

64구역 이상 + 유효한 유한 경계 + 결정표 메모리 제한 이내
  → 생성자에서 좌표 경계 압축 결정표 생성
  → 객체마다 x/y 이진 탐색 2회와 배열 조회 1회

비유한/역전 경계 또는 결정표 메모리 제한 초과
  → 기존 선형 비교
```

아래 값은 수정 전 프로덕션 소스로 만든 기준 실행 파일과 수정 후 프로덕션 소스로 만든 실행
파일의 비교다. 수정 전·후 각각 프로그램을 3회 독립 실행했고, 각 실행 내부에서 9개 측정값의
중앙값을 구한 뒤 세 실행의 중앙값을 사용했다.

| 구역 | 객체 | 최적화 전 | 최적화 후 | 배속 | 지연 감소 |
|---:|---:|---:|---:|---:|---:|
| 4 | 16 | 57.25 ns | 49.01 ns | 1.17× | 14.39% |
| 4 | 64 | 213.32 ns | 170.63 ns | 1.25× | 20.01% |
| 4 | 256 | 725.51 ns | 701.48 ns | 1.03× | 3.31% |
| 4 | 1,024 | 2,880.20 ns | 2,806.40 ns | 1.03× | 2.56% |
| 16 | 1,024 | 8,896.47 ns | 8,907.40 ns | 1.00× | -0.12% |
| 64 | 1,024 | 29,294.60 ns | 11,588.00 ns | 2.53× | 60.44% |
| 256 | 1,024 | 126,600.67 ns | 13,318.67 ns | 9.51× | 89.48% |

16구역의 `-0.12%`는 개선으로 표시하지 않는다. 현재 측정 분해능과 독립 실행 변동 범위 안의
사실상 동일한 결과다. 실제 기본 구성인 4구역은 객체 수에 따라 2.56~20.01% 개선됐다.

계산식:

```text
배속 = 최적화 전 시간 / 최적화 후 시간
지연 감소율(%) = (1 - 최적화 후 시간 / 최적화 전 시간) × 100
```

256구역·1,024객체의 계산:

```text
배속 = 126,600.67 / 13,318.67 = 9.51배
지연 감소율 = (1 - 13,318.67 / 126,600.67) × 100 = 89.48%
```

## 2. 첫 시도에서 폐기한 접근

처음에는 4구역 이하에서 객체마다 `switch`를 실행하고 8구역부터 결정표를 사용했다. 측정 결과:

- 4구역: 객체별 `switch` 비용으로 일부 케이스가 약 30% 느려짐
- 16구역: 결정표 이진 탐색 비용이 짧은 선형 탐색보다 큼

따라서 해당 구현은 유지하지 않았다. 최종 구현은 다음처럼 조정했다.

- 4구역 분기는 객체 루프 밖에서 프레임당 한 번만 실행
- 16구역은 기존 선형 경로
- 명확한 이득이 측정된 64구역부터 결정표 사용

## 3. 4구역 고정 비교

기본 `channelCount=4` 구성에서는 네 `SpatialZone`을 선언 순서대로 직접 비교한다.

```text
zone[0] 포함 → zone[0]
아니면 zone[1] 포함 → zone[1]
아니면 zone[2] 포함 → zone[2]
아니면 zone[3] 포함 → zone[3]
아니면 -1
```

구역이 겹치더라도 먼저 선언된 구역이 선택되며, 기존 first-match와 같다. GCC/Clang에서는 이
작은 선형 경로를 호출부에 인라인하도록 힌트를 주고, 그 외 컴파일러에서는 표준 `inline`으로
폴백하므로 특정 컴파일러 문법 때문에 빌드가 깨지지 않는다.

## 4. 64구역 이상 좌표 결정표

### 좌표 압축

모든 유효 구역의 `minX`, `maxX`, `minY`, `maxY`를 정렬하고 중복을 제거한다. 각 축은 다음
버킷으로 분리된다.

```text
첫 경계 전 열린 구간
경계값 자체
경계 사이 열린 구간
...
마지막 경계값
마지막 경계 후 열린 구간
```

경계값 자체를 별도 버킷으로 두기 때문에 기존의 `>= min`, `<= max` 경계 포함 규칙을 그대로
표현한다.

### first-match 보존

결정표는 구역을 선언 순서의 역순으로 기록한다. 뒤 구역을 먼저 쓰고 앞 구역이 나중에 덮어쓰므로
최종 셀에는 가장 먼저 선언된 포함 구역의 인덱스가 남는다.

`zoneId` 자체가 아니라 `zones_`의 원래 인덱스를 저장한다. 따라서 `zoneId=-1`인 구역이 먼저
매칭되는 비정상 직접 생성 입력도 기존처럼 탐색을 중단하고 최종 `-1` 및 미배정 로그를 남긴다.

### 메모리 제한

결정표는 `uint32_t` 구역 인덱스를 저장하며 최대 셀 수를 1,100,000개로 제한한다.

```text
최대 결정표 데이터 = 1,100,000 × 4 byte = 4,400,000 byte
약 4.20 MiB
```

한도를 넘으면 생성에 실패하거나 메모리를 과도하게 쓰는 대신 기존 선형 탐색으로 폴백한다.

벤치마크의 규칙적인 구역 배치에서는 다음 크기다.

```text
64구역: 33 × 33 = 1,089셀 ≈ 4.25 KiB
256구역: 65 × 65 = 4,225셀 ≈ 16.50 KiB
```

## 5. 기능 동일성 검증

추가 파일:

```text
tests/control-server/ZoneTestSupport.h
tests/control-server/unit/ZoneMapperEquivalenceTest.cpp
performance/ZoneBenchmark.cpp
```

테스트 결과:

```text
[==========] 5 tests from 1 test suite ran.
[  PASSED  ] 5 tests.
```

검증 범위:

1. first-match 선언 순서
2. `minX`, `maxX`, `minY`, `maxY` 경계 포함
3. 겹치는 구역
4. 어느 구역에도 속하지 않는 객체의 `zoneId=-1`
5. 매칭 구역 자체의 `zoneId=-1`
6. `NaN`, `+Inf`, `-Inf` 객체 좌표
7. 비유한 구역 경계
8. `min > max` 역전 구역
9. 64구역 이상 인덱스 경로의 겹침과 정확한 경계
10. 결정표 메모리 제한 초과 시 선형 폴백
11. 고정 시드 `0x5A4F4E454D415050`의 500개 무작위 구역·객체 입력

최종 테스트 실행 시간은 현재 머신에서 약 120 ms였으며 5개 테스트가 모두 통과했다.
`AppContext.cpp`도 변경된 헤더를 사용해 `-fsyntax-only` 컴파일을 통과했다.

## 6. 벤치마크 방법

수정 전에 원래 `SpatialZoneMapper.cpp`를 직접 컴파일해 기준 실행 파일을 먼저 만들고 3회
측정했다. 그 후 프로덕션 코드를 수정하고 동일한 `ZoneBenchmark.cpp`로 다시 컴파일·측정했다.

환경:

- 컴파일러: MinGW-w64 GCC 13.1.0
- 옵션: `-std=c++20 -O2 -DNDEBUG -pthread`
- 운영체제: Windows NT 10.0.26200, x64
- 프로세서 식별자: Intel64 Family 6 Model 140 Stepping 1
- 논리 프로세서: 8
- 각 trial 전 워밍업: 50회
- 각 케이스: 9개 trial 중앙값
- 수정 전·후 각각 3회 독립 실행 후 중앙값
- 생성자와 결정표 생성 시간: steady-state 프레임 지연에서 제외
- 모든 객체는 로그 비용이 섞이지 않도록 반드시 하나의 구역 내부에 배치

객체는 각 구역 중앙에 순환 배치했다. 따라서 선형 구현은 구역 수가 늘수록 평균적으로 더 많은
사각형을 검사하고, 결정표 구현은 구역 수와 무관하게 축별 이진 탐색과 배열 조회를 수행한다.

## 7. 한계

이번 숫자는 Windows/MinGW의 합성 입력 결과이며 배포 Raspberry Pi/Linux의 절대 지연시간이
아니다. 특히 4구역 경로는 절대 시간이 수십~수천 ns라 운영체제 스케줄링과 CPU 주파수 변화의
영향을 크게 받는다. 16구역의 `-0.12%`처럼 1% 미만 차이는 성능 변화로 해석하면 안 된다.

결정표 생성 시간은 서버 시작 시 한 번 발생하므로 프레임 hot path 표에서는 제외했다. 구역
설정을 런타임에 매 프레임 재생성하는 사용 방식이라면 이 결과를 적용할 수 없다. 현재
`AppContext`는 서버 조립 시 `SpatialZoneMapper`를 한 번 생성한다.

5개 명시적 테스트와 500개 무작위 입력의 일치는 강한 회귀 증거지만 모든 가능한 `double`
조합에 대한 형식적 증명은 아니다. 비유한·역전 구역과 메모리 한도 초과는 의도적으로 기존
선형 경로를 사용해 결정표의 전제 밖 입력을 격리했다.

현재 머신에는 저장소의 기존 Linux 전체 빌드 캐시가 요구하는 `/usr/bin/cmake`,
`/usr/bin/c++`, 시스템 `nlohmann_json`, `libmosquitto` 조합이 없다. 따라서 전체 서버 링크는
실행하지 못했다. 대신 변경된 zone 프로덕션 소스를 직접 컴파일·링크하고, GTest를 실행하고,
실제 조립 코드인 `AppContext.cpp`의 구문 컴파일을 확인했다.
