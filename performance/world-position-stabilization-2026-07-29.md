# Control-server 월드 좌표 안정화 보고서

- 작성일: 2026-07-29
- 대상:
  - `control-server/src/fuse/GridFuser.cpp`
  - `control-server/src/fuse/GridFuser.h`
  - `control-server/include/core/AppConfig.h`
  - `control-server/src/core/AppContext.cpp`
- 적용 기본값: `risk.positionJitterRadius = 0.15` m

## 1. 결론

같은 `gid`의 월드 좌표를 매 윈도우의 원시 관측 평균으로 즉시 덮어쓰던 경로에 공간
히스테리시스를 적용했다.

±0.20m 합성 정지 잡음에서 프레임 사이 RMS 이동량은 다음과 같이 감소했다.

```text
0.232256 m/frame → 0.056162 m/frame
감소율 = 75.82%
```

처리 지연은 객체 수별 paired 비교 중앙값에서 `-0.41%~+3.74%`로 측정됐다. 방향이
일관되지 않아 필터가 처리량을 개선한다고 주장할 수 없으며, 현재 Windows 측정 변동 안에서
최대 관측 오버헤드는 3.74%였다.

## 2. 문제 원인

기존 `GridFuser`는 여러 채널 관측을 평균해 월드 좌표를 만든 뒤 `gid`를 유지했지만,
추적 상태의 좌표는 매 100ms 윈도우마다 새 평균으로 즉시 교체했다.

```cpp
entity.pos = object.pos;
```

따라서 대상이 정지해도 다음 요인이 그대로 출력 좌표 변화가 됐다.

- 상류 검출 및 지면점 추출 오차
- 프레임마다 달라지는 채널별 관측 오차
- 가려짐으로 융합 클러스터에 참여하는 카메라 구성이 달라지는 경우

이번 저장소에는 실제 MQTT 좌표 기록이 없어 각 원인의 현장 기여율은 확인할 수 없다.
코드에서 확인되는 직접 원인은 시간축 좌표 안정화가 없다는 점이다.

## 3. 적용 알고리즘

이전 안정화 출력 위치를 `P`, 현재 원시 융합 위치를 `R`, 설정 반경을 `r`이라고 한다.

```text
distance(P, R) <= r
  → 출력 = P

distance(P, R) > r
  → R 방향으로 이동
  → 최종 출력과 R 사이 거리는 r
```

수식:

```text
d = |R - P|

d <= r:
  output = P

d > r:
  output = P + (R - P) × ((d - r) / d)
```

EMA처럼 시간에 따라 지연이 계속 누적되지 않는다. 유한한 정상 좌표에서 출력과 현재 원시
좌표 사이의 공간 지연은 설정 반경 `r` 이하로 제한된다.

### 원시 좌표와 안정화 좌표 분리

추적 상태는 두 좌표를 따로 저장한다.

```text
rawPos
  → gid 거리 매칭 및 trackMaxDistance 판정

pos
  → zone, risk, MQTT/UI 출력
```

안정화 좌표를 `gid` 거리 매칭에 사용하면 필터 지연 때문에 정상 이동이
`trackMaxDistance`를 초과한 것처럼 보일 수 있다. 이를 막기 위해 매칭은 기존과 같은 원시
좌표를 사용한다.

## 4. 안정성 지표 전후 비교

입력:

- 실제 위치: `(25.0, -10.0)` m
- 각 축 독립 균등 잡음: `[-0.20, +0.20]` m
- 프레임 수: 5,000
- 간격: 100ms
- 고정 난수 시드: `0x53544142494C495A`
- 비활성: `positionJitterRadius=0`
- 활성: `positionJitterRadius=0.15`

| 지표 | 안정화 전 | 안정화 후 | 감소율 |
|---|---:|---:|---:|
| 위치 RMS 오차 | 0.164272 m | 0.066136 m | 59.74% |
| 프레임 간 RMS 이동량 | 0.232256 m | 0.056162 m | 75.82% |
| 최대 단일 프레임 이동량 | 0.516612 m | 0.216831 m | 58.03% |

계산식:

```text
감소율(%) = (1 - 안정화 후 / 안정화 전) × 100
```

프레임 간 RMS 이동량 계산:

```text
(1 - 0.056162 / 0.232256) × 100 = 75.82%
```

이 결과는 고정 시드 합성 입력의 결과다. 실제 카메라 좌표 튐이 같은 분포라고 주장할 수 없다.

## 5. 처리 지연 전후 비교

같은 trial에서 필터 비활성·활성을 모두 측정하고 trial마다 오버헤드 비율을 계산했다.
측정 순서는 trial마다 교대했다. 각 프로그램 실행에서 9개 trial의 중앙값을 구하고,
프로그램을 3회 독립 실행한 뒤 다시 중앙값을 사용했다.

| 객체/프레임 | 안정화 전 | 안정화 후 | paired 오버헤드 중앙값 |
|---:|---:|---:|---:|
| 1 | 676.32 ns | 667.70 ns | +3.74% |
| 64 | 25,311.33 ns | 25,566.67 ns | -0.41% |
| 256 | 116,024.00 ns | 118,980.00 ns | +1.81% |

`paired 오버헤드 중앙값`은 각 trial에서 다음 식으로 먼저 계산한 값의 중앙값이다.

```text
paired 오버헤드(%) = (활성 시간 / 비활성 시간 - 1) × 100
```

따라서 표의 독립적인 전·후 중앙값 비율과 paired 오버헤드가 정확히 같지는 않다.
64객체의 음수 값처럼 방향이 실행마다 바뀌었으므로 작은 차이는 개선이 아니라 측정 잡음으로
해석해야 한다.

### 지연 측정 입력

- 한 채널에 동일한 안정 ID를 가진 1, 64, 256개 객체
- 객체 간격: 3m
- 연속 프레임 좌표 오프셋: `-0.05m`, `+0.05m` 교대
- 워밍업: trial마다 두 경로 각각 100프레임
- trial: 케이스별 9회
- 반복:
  - 1객체: trial당 5,000프레임
  - 64객체: trial당 300프레임
  - 256객체: trial당 50프레임

## 6. 설정

`RiskConfig`에 다음 항목을 추가했다.

```json
{
  "risk": {
    "positionJitterRadius": 0.15
  }
}
```

동작:

- `0`: 좌표 안정화 비활성, 기존 원시 좌표 출력
- 양의 유한값: 해당 반경(m)의 공간 히스테리시스 적용
- 음수 또는 비유한값: 설정 로드 시 경고 후 `0`으로 보정

실제 현장 좌표 기록이 없으므로 기본 `0.15m`는 경험적으로 검증된 현장 최적값이 아니다.
배포 후 정지 대상의 원시 좌표 로그를 수집해 잡음 분포와 zone 경계 요구사항에 맞게 조정해야
한다.

## 9. 한계와 안전상 주의

- 실제 카메라 녹화나 MQTT 좌표 로그가 없어 `0.15m`가 현장 최적값인지 확인할 수 없다.
- 안정화 좌표가 zone과 risk 계산에 사용되므로 zone 경계 통과와 거리 변화가 최대 설정 반경만큼
  공간적으로 지연될 수 있다.
- 이 필터는 검출·호모그래피·카메라 외부 캘리브레이션 오류 자체를 고치지 않는다. 체계적인
  좌표 오프셋이 있으면 캘리브레이션을 수정해야 한다.
- 합성 테스트와 500개 무작위 윈도우는 강한 회귀 증거지만 모든 `double` 입력 조합의 수학적
  증명은 아니다.
- 실제 배포 Linux/Raspberry Pi의 처리 지연과 CPU 사용률은 측정하지 않았다.
