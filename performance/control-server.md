## 3. Core

### 3.1 최종 판단

`core` 프로덕션 코드에는 측정으로 입증된 최적화 변경을 적용하지 않았다.

검토한 후보는 집계 콜백이 소유한 `std::vector<veda::TopViewFrame>`을
`processPipeline()`의 값 매개변수로 한 번 더 이동하는 경계를 `const&` 전달로 바꾸는
것이었다.

```cpp
// 현재 구현
[this](std::vector<veda::TopViewFrame> frames) {
    this->processPipeline(std::move(frames));
}

void Controller::processPipeline(std::vector<veda::TopViewFrame> frames);
```

```cpp
// 검토했으나 적용하지 않은 후보
[this](std::vector<veda::TopViewFrame> frames) {
    this->processPipeline(frames);
}

void Controller::processPipeline(
    const std::vector<veda::TopViewFrame>& frames);
```

### 3.2 후보 변경 전후 지표

동일 실행 파일을 3회 독립 실행했다. 각 실행에서 11개 측정값의 중앙값을 구한 뒤 세 실행의
중앙값을 사용했다.

| 프레임 수 | 현재 값 전달 | 후보 `const&` 전달 | 배속 | 지연 감소율 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 58.57 ns | 61.91 ns | 0.95배 | -5.70% |
| 4 | 59.36 ns | 59.11 ns | 1.00배 | 0.42% |
| 16 | 85.92 ns | 89.20 ns | 0.96배 | -3.82% |
| 64 | 157.93 ns | 163.84 ns | 0.96배 | -3.74% |

4프레임 계산:

```text
배속 = 59.36 / 59.11 = 1.0042배
지연 감소율 = (1 - 59.11 / 59.36) × 100 = 0.42%
절대 차이 = 59.36 - 59.11 = 0.25 ns/call
```

독립 실행 변동:

| 프레임 수 | 현재 3회 범위 | 후보 3회 범위 |
| ---: | ---: | ---: |
| 1 | 58.32~59.61 ns | 58.95~62.58 ns |
| 4 | 56.24~63.88 ns | 55.08~60.77 ns |
| 16 | 69.95~88.28 ns | 87.63~107.68 ns |
| 64 | 155.71~166.87 ns | 150.66~168.97 ns |

4프레임의 `0.25 ns` 차이는 현재 구현의 실행 범위 `7.64 ns`와 후보 실행 범위 `5.69 ns`보다
작다. 따라서 통계적으로 유의한 개선이라고 판정할 근거가 없다.

### 3.3 변경하지 않은 이유

- `Controller`는 transform → fuse → zone → risk → dispatch → sink를 순서대로 호출하는
  오케스트레이터이며, 객체 수에 비례하는 주요 계산은 하위 모듈에 있다.
- 출력 버퍼 `observations_`는 이미 멤버로 재사용한다.
- 상태 callback의 lock 범위는 스냅샷 갱신으로 제한되어 있고 로그 및 MQTT 발행은 lock 밖이다.
- `AppContext::buildController()`는 시작 시 한 번 실행되므로 생성자 미세 조정은 steady-state
  프레임 지연을 줄이지 않는다.
- 파이프라인 병렬화는 전역 ID 추적 상태와 단계별 출력 순서를 바꿀 수 있어 기능 불변 조건을
  만족한다고 입증되지 않았다.

## 4. Fuse

### 4.1 적용 내용

운영 조립 코드가 `ConcatFuser` 대신 적응형 `GridFuser`를 사용한다.

```text
후보 수 < 96
  → 기존과 같은 순서의 전체 쌍 비교

후보 수 >= 96이며 안전하게 격자화 가능
  → 공간 해시의 3×3 인접 셀에서 후보 수집
  → (i, j) 사전순 정렬
  → 기존과 같은 순서로 union

비유한 좌표, 극단 좌표 또는 NaN 임계값
  → 기존 전체 쌍 비교 경로로 폴백
```

`ConcatFuser`는 기준 구현과 회귀 비교 대상으로 보존한다. 16,384개 해시 버킷은 큰 정상 입력이
처음 들어왔을 때 한 번만 지연 할당한다.

### 4.2 최적화 전후 지표

4채널 중첩 관측 합성 입력을 사용했다. 각 독립 실행에서 9개 측정값의 중앙값을 구하고 프로그램을
3회 독립 실행한 뒤 다시 중앙값을 사용했다. 좌표 안정화 비용을 분리하기 위해
`positionJitterRadius=0` 조건으로 측정했다.

| 전체 관측 객체 | 실제 객체 | 최적화 전 `ConcatFuser` | 최적화 후 `GridFuser` | 배속 | 지연 감소 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 64 | 16 | 12.011 µs/frame | 11.807 µs/frame | 1.02배 | 1.70% |
| 128 | 32 | 38.721 µs/frame | 23.588 µs/frame | 1.64배 | 39.08% |
| 256 | 64 | 143.673 µs/frame | 46.717 µs/frame | 3.08배 | 67.48% |
| 512 | 128 | 500.936 µs/frame | 108.138 µs/frame | 4.63배 | 78.41% |
| 1,024 | 256 | 2,038.790 µs/frame | 198.310 µs/frame | 10.28배 | 90.27% |

1,024개 입력 계산:

```text
배속 = 2,038.790 / 198.310 = 10.28배
지연 감소율 = (1 - 198.310 / 2,038.790) × 100 = 90.27%
```

### 4.3 비교량

기준 구현의 최대 비교 쌍:

```text
N × (N - 1) / 2
```

| 전체 관측 `N` | 기준 최대 비교 쌍 | 그리드 근접 쌍 |
| ---: | ---: | ---: |
| 64 | 2,016 | 작은 입력 폴백으로 2,016 |
| 128 | 8,128 | 192 |
| 256 | 32,640 | 384 |
| 512 | 130,816 | 768 |
| 1,024 | 523,776 | 1,536 |

그리드 경로도 해시 충돌로 먼 후보를 확인할 수 있으며 최종 병합 전 실제 거리를 다시 계산한다.
위 근접 쌍 수는 충돌이 없는 벤치마크 입력에서의 값이다.

### 4.4 월드 좌표 튐 안정화

같은 `gid`의 이전 출력 위치를 `P`, 현재 원시 융합 위치를 `R`, 안정화 반경을 `r`이라고 한다.

```text
d = |R - P|

d <= r:
  output = P

d > r:
  output = P + (R - P) × ((d - r) / d)
```

`rawPos`는 기존 `gid` 거리 매칭과 `trackMaxDistance` 판정에 사용하고, 안정화된 `pos`는
zone·risk·MQTT/UI 출력에 사용한다. 기본 설정은 `risk.positionJitterRadius=0.15m`이며 `0`이면
기존 원시 좌표 출력 동작으로 돌아간다.

고정 시드의 ±0.20m 정지 잡음 5,000프레임 결과:

| 안정성 지표 | 안정화 전 | 안정화 후 | 감소율 |
| :--- | ---: | ---: | ---: |
| 위치 RMS 오차 | 0.164272 m | 0.066136 m | 59.74% |
| 프레임 간 RMS 이동량 | 0.232256 m | 0.056162 m | **75.82%** |
| 최대 단일 프레임 이동량 | 0.516612 m | 0.216831 m | 58.03% |

프레임 간 RMS 이동량 계산:

```text
(1 - 0.056162 / 0.232256) × 100 = 75.82%
```

처리비용:

| 객체/프레임 | 안정화 전 | 안정화 후 | paired 오버헤드 중앙값 |
| ---: | ---: | ---: | ---: |
| 1 | 676.32 ns | 667.70 ns | +3.74% |
| 64 | 25,311.33 ns | 25,566.67 ns | -0.41% |
| 256 | 116,024.00 ns | 118,980.00 ns | +1.81% |

오버헤드의 방향이 실행마다 일관되지 않았다. 필터가 처리량을 개선한다고 주장할 수 없으며,
현재 Windows 측정에서 관측된 최대 오버헤드는 3.74%다.

## 5. Transform

### 5.1 적용 내용

`AffineLocalToWorldTransform`의 좌표식, 캘리브레이션 선택, 미보정 채널 정책, 월드 경계 필터링과
출력 순서를 유지하면서 다음 비용을 제거했다.

1. 유한한 카메라 방위각의 회전계수를 생성자에서 한 번만 계산한다.
2. `NaN` 또는 `±Inf` 방위각은 기존과 동일하게 호출마다 삼각함수를 계산해 IEEE-754 동작을 보존한다.
3. 바깥 프레임 벡터와 프레임별 객체 벡터의 capacity를 다음 윈도우에서 재사용한다.
4. 월드 경계 검사가 꺼지면 출력 크기를 한 번에 맞추고 인덱스로 직접 기록한다.
5. 경계 검사가 켜지면 기존처럼 범위 밖 객체를 폐기하고 통과 객체만 순서대로 기록한다.

- 생성자 시간 제외

## 6. Zone

### 6.1 적용 내용

`SpatialZoneMapper`의 선언 순서 first-match, 경계 포함, 미배정 `zoneId=-1`과 출력 순서를
유지하면서 구역 수에 따라 실행 경로를 선택한다.

```text
정확히 4구역
  → 객체 루프 밖에서 한 번 분기
  → 네 구역을 선언 순서대로 고정 비교

0~63구역(4구역 제외)
  → 기존 선형 비교

64구역 이상이며 경계와 메모리 조건이 유효
  → 생성자에서 좌표 압축 결정표 생성
  → 객체마다 x/y 이진 탐색 2회와 배열 조회 1회

비유한·역전 경계 또는 결정표 한도 초과
  → 기존 선형 비교로 폴백
```

첫 시도의 객체별 `switch`와 8구역 이상 결정표는 4구역 일부 케이스를 약 30% 느리게 만들고
16구역에서도 이득이 없어 폐기했다. 최종 구현은 측정으로 이득이 확인된 경로만 남겼다.

### 6.2 최적화 전후 지표

수정 전·후 프로덕션 소스를 각각 직접 컴파일했다. 각 실행의 9개 trial 중앙값과 전후 각각
3회 독립 실행의 중앙값을 사용했다.

| 구역 | 객체 | 최적화 전 | 최적화 후 | 배속 | 지연 감소 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 16 | 57.25 ns | 49.01 ns | 1.17배 | 14.39% |
| 4 | 64 | 213.32 ns | 170.63 ns | 1.25배 | 20.01% |
| 4 | 256 | 725.51 ns | 701.48 ns | 1.03배 | 3.31% |
| 4 | 1,024 | 2,880.20 ns | 2,806.40 ns | 1.03배 | 2.56% |
| 16 | 1,024 | 8,896.47 ns | 8,907.40 ns | 1.00배 | -0.12% |
| 64 | 1,024 | 29,294.60 ns | 11,588.00 ns | 2.53배 | 60.44% |
| 256 | 1,024 | 126,600.67 ns | 13,318.67 ns | 9.51배 | 89.48% |

16구역의 `-0.12%`는 측정 변동 안의 사실상 동일한 결과이며 개선으로 판정하지 않는다. 현재
기본 구성인 4구역은 객체 수에 따라 2.56~20.01% 지연이 감소했다.

256구역·1,024객체 계산:

```text
배속 = 126,600.67 / 13,318.67 = 9.51배
지연 감소율 = (1 - 13,318.67 / 126,600.67) × 100 = 89.48%
```

### 6.3 결정표의 기능 보존과 메모리 제한

- 경계값 자체를 별도 버킷으로 만들어 `>= min`, `<= max` 규칙을 보존한다.
- 구역을 선언 순서의 역순으로 기록하고 앞 구역이 뒤 구역을 덮어쓰게 해 first-match를 보존한다.
- `zoneId`가 아니라 원래 `zones_` 인덱스를 저장해 `zoneId=-1`인 비정상 입력의 기존 동작도 유지한다.
- 결정표는 `uint32_t` 인덱스 최대 1,100,000셀, 약 4.20MiB로 제한한다.
- 한도를 넘거나 경계가 전제 조건을 만족하지 않으면 선형 경로로 폴백한다.

### 6.4 검증

- first-match와 네 경계의 포함 규칙
- 겹치는 구역과 미배정 `zoneId=-1`
- `NaN`, `+Inf`, `-Inf` 객체 좌표
- 비유한 및 `min > max` 역전 구역
- 64구역 이상 결정표 경로의 겹침과 정확한 경계
- 결정표 메모리 한도 초과 시 선형 폴백
- 고정 시드 500개 무작위 구역·객체 입력
- warm path 무할당

최종 결과: **7개 테스트 통과**

## 7. 공통 측정 환경과 해석 제한

| 항목 | 값 |
| :--- | :--- |
| 운영체제 | Microsoft Windows NT 10.0.26200.0, x64 |
| 컴파일러 | MinGW-w64 GCC 13.1.0 |
| 기본 최적화 옵션 | `-std=c++20 -O2 -DNDEBUG` |
| 프로세서 식별자 | Intel64 Family 6 Model 140 Stepping 1 |
| 논리 프로세서 | 8 |
| 집계 방식 | 각 실행의 trial 중앙값을 구한 뒤 3회 독립 실행값의 중앙값 사용 |

해석 시 다음 제한을 적용한다.

1. 표의 값은 Windows/MinGW 합성 입력의 steady-state 결과이며 배포 Raspberry Pi/Linux의 절대
   지연시간이 아니다.
2. 1% 미만의 차이나 독립 실행 변동보다 작은 차이는 성능 개선으로 판정하지 않는다.
3. 생성자 및 최초 캐시·결정표 할당 비용은 프레임 hot path 지연에서 제외했다.
4. 고정 시드 무작위 입력과 명시적 경계 테스트는 강한 회귀 증거지만 모든 `double` 입력 조합의
   형식적 증명은 아니다.
5. 월드 좌표 안정화의 `0.15m` 기본값은 현장 로그로 검증한 최적값이 아니다. 실제 배포 후 정지
   대상의 원시 좌표 분포와 zone 경계 요구사항에 맞춰 재조정해야 한다.
6. 안정화는 검출·지면점 추출·카메라 외부 캘리브레이션의 체계적 오차를 수정하지 않는다.
7. 배포 판단 전 타깃 장비의 고정 CPU 조건과 실제 MQTT 프레임 기록으로 동일 벤치마크를 다시
   수행해야 한다.
