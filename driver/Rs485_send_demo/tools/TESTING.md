# 테스트 가이드라인 — Rs485_send_demo

스케줄러(`sched_select.inc`, `sched_task`)를 고칠 때 무엇을 어디서 확인하는지에 대한 규칙.
이 프로젝트에 한정된 문서다. 일반론이 아니라 여기서 실제로 겪은 고장을 기준으로 썼다.

## 층 나누기

확인하려는 것에 따라 층이 정해진다. **아래층에서 잡히는 건 위층으로 올리지 않는다** — 굽는 데 1분,
실기 재현에 10분 걸리는 것을 gcc 1초로 끝낼 수 있으면 그게 맞다.

| 층 | 무엇을 잡나 | 어디서 |
|---|---|---|
| 1. 호스트 단위 테스트 | 선택 규칙, 우선순위, 굶주림, 시간 계산 | `tools/test_sched_select.c` |
| 1. 호스트 단위 테스트 | ACK 줄 조립·해석 (ISR 문맥이라 실기 관찰 불가) | `tools/test_ack_parse.c` |
| 1.5 호스트 닫힌-루프 sim | 상태 전이(applied/retry), 수렴, 고장 격리, 복구, **지연 상한** | `tools/test_sched_loop.c` |
| 2. 온타깃 + 가짜 전송로 | 스택, 틱 주기 실측, volatile/최적화, 태스크 경합 | 보드 + UART 로그 / GPIO 토글 |
| 3. 실기 수용 테스트 | 복구, 동기, 사람이 보는 동작 | RPi + Slave 2대 |

## 1층 규칙

**빌드/실행** (`tools/`에서):

```sh
gcc -Wall -Wextra -I../Core/Inc test_sched_select.c -o test_sched_select && ./test_sched_select
```

통과하면 `sched_select: all checks passed` 한 줄. 실패하면 assert가 파일:줄로 멈춘다.
스케줄러 로직을 건드렸으면 **커밋 전에 이 한 줄을 돌린다.**

### 테스트가 진짜 보고 있는지 확인 — `mutation_check.py`

```sh
python3 mutation_check.py
```

"전부 통과"는 **코드가 옳은 것**과 **테스트가 아무것도 안 보는 것**을 구분하지 못한다.
이 스크립트는 펌웨어를 일부러 망가뜨린 사본으로 테스트를 돌려 그 둘을 가른다.
현재 코드 뮤턴트 7 + 상수 회귀 3, **전부 검출**.

실제로 이 검사가 세 개의 구멍을 찾아냈다:

1. **커서 전진을 지워도 통과했다** — 한 번에 한 채널만 어긋나면 커서가 없어도 결국 다
   처리되기 때문. → 두 채널을 동시에 계속 어긋나게 두는 `test_cursor_advances_between_contenders` 추가
2. **DANGER 우선 패스 호출을 지워도 통과했다** — `test_sched_select.c` 는 `pick_pending()` 을
   직접 부르므로 "`sched_tick()` 이 1차 패스를 부르는가"는 아무도 안 봤다.
   → `test_danger_dispatched_first` 추가
3. **리프레시를 2000 → 20000ms 로 늘려도 통과했다** — 두 가지 이유가 겹쳐 있었다.
   (a) 합격선을 `SCHED_REFRESH_MSEC * 2` 로 파생시켜서 검사 대상이 커지면 합격선도 같이 커졌다.
   (b) 부하 구간에서는 33ms 랜덤 명령이 채널을 계속 건드려 리프레시가 죽어도 티가 안 났고,
   공백은 송신이 일어난 순간에만 기록돼 "아예 안 온 경우"가 0 으로 남았다.
   → 합격선을 절대값(4000ms)으로 고정 + 조용한 구간 측정 추가 + 미결 공백도 함께 계산

> **합격선을 검사 대상에서 파생시키지 말 것.** 상수를 바꾸면 합격선이 따라 움직여 검사가
> 조용히 무력해진다. 뮤테이션 검사가 없었으면 못 찾았을 종류의 결함이다.

**여러 줄 패턴은 sed 로 손대지 말 것.** 매칭이 안 돼 파일이 그대로인데 "통과했다 = 구멍이다"로
잘못 읽은 적이 있다. `mutation_check.py` 의 `apply()` 는 치환이 안 되면 그 자리에서 멈춘다.

지켜야 할 네 가지:

1. **복사본을 만들지 않는다.** 테스트는 `#include "sched_select.inc"`로 펌웨어와 *같은 소스*를 부른다.
   규칙을 복사해서 테스트에 다시 적으면, 펌웨어만 고쳤을 때 테스트가 조용히 통과한다.
2. **시간은 테스트가 정한다.** `osKernelGetTickCount()`를 `fake_now`로 대체한다. 리프레시 2초,
   백오프 100ms, 틱 접힘(49일)을 전부 대입 한 줄로 만들 수 있어야 한다. 실제로 기다리는 테스트는 쓰지 않는다.
3. **프레임워크를 넣지 않는다.** `assert.h` + `main()`에서 순서대로 호출. 이 규모에서 Unity/Ceedling은
   파일만 늘고 잡는 버그는 같다.
4. **테스트 이름이 곧 고장 이름이다.** `test_failing_danger_does_not_starve_others` 처럼 깨졌을 때
   실기에서 어떻게 보이는지를 주석에 적는다. 반년 뒤에 이 assert를 지워도 되는지 판단하는 근거가 그것뿐이다.

### 알려진 구멍 — 테스트 더블 (1.5층이 메운다)

1층 테스트의 `commit()` / `fail()`은 `dispatch_channel()`의 상태 전이를 **손으로 흉내낸 것**이다
(`test_sched_select.c` 하단). `dispatch_channel()`이 `applied_risk` / `last_tx_tick` / `retry`를
저것과 다르게 갱신하면 **1층은 통과하는데 실기는 틀린다.**

**1.5층(`test_sched_loop.c`)이 바로 이 구멍을 메운다.** 손으로 흉내내는 대신 `sched_dispatch.inc`
(실제 `dispatch_channel()` / `sched_tick()`)를 그대로 포함하고, 하드웨어/RTOS 와 닿는 seam 여섯 개만
가짜로 갈아끼운다:

```
send_channel_command / wait_for_slave_ack / drain_ack_queue /
enqueue_uplink / risk_to_status / (osMutex*·osKernelGetTickCount)
```

가짜 Slave 모델(reachable / will_ack / applied)로 이 seam 을 구동하고, RPi 를 흉내내 33ms 마다
랜덤 위험 이벤트를 던진다(카메라 30fps). 두 개의 가상 클럭(주입 33ms / 틱 20ms)으로 실제 대기 없이
돌리므로 300 시드 × 30초 소크가 0.1초 안에 끝난다.

검사하는 네 가지:

1. **수렴** — 랜덤을 퍼부은 뒤 주입을 멈추면 모든 채널이 desired 대로 update 된다.
2. **고장 격리** — Slave 한 대가 죽어 DANGER 로 우선 패스를 독점해도 산 보드 채널은 굶지 않는다
   (`SCHED_RETRY_BACKOFF_MSEC` 회귀 테스트). 죽은 채널은 ACK 가 없으므로 applied 가 거짓으로 갱신되지 않는다.
3. **복구** — 죽었던 Slave 가 돌아오면 RPi 개입 없이 스스로 맞춘다.
4. **리프레시 재동기** — Slave 가 조용히 리셋돼도 `SCHED_REFRESH_MSEC` 안에 상태를 다시 밀어 넣는다.

**빌드/실행** (`tools/`에서):

```sh
gcc -Wall -Wextra -I../Core/Inc test_sched_loop.c -o test_sched_loop && ./test_sched_loop
```

랜덤이므로 **시드를 고정한다**(`srand(seed)`). 실패하면 `FAIL (seed=.. t=..ms): ...` 로 시드와
시각을 찍고 멈추므로, 그 시드 하나만 다시 돌리면 정확히 재현된다.

**남은 주의점:** 1.5층의 seam(가짜 send/ack/risk_to_status)이 실기 함수와 의미가 갈라지면 여전히
"통과하는데 틀린" 상태가 될 수 있다. seam 은 `sched_dispatch.inc` 맨 위 주석에 목록으로 고정해 두었다 --
그 여섯 개의 계약을 바꾸면 이 파일의 가짜 구현도 같이 본다. `dispatch_channel()` 자체의 상태 갱신
순서를 바꾸는 것은 이제 1.5층이 실제 소스로 검증하므로 안전하다.

### 가짜 seam 은 '시간'까지 모델링해야 한다 (실제로 버그를 놓쳤던 지점)

처음에는 가짜 `wait_for_slave_ack()` 가 즉답했다. 그래서 **실패한 ACK가 공짜**였고, 실기에서 가장 크게
밀리는 구간(타임아웃 100ms)이 시뮬레이션에서 통째로 사라졌다. 그 상태로는 아래 버그가 통과했다.

`TX_TIME_MSEC` / `ACK_REPLY_MSEC` / `RS485_ACK_TIMEOUT_MSEC` 만큼 `fake_now` 를 실제로 전진시키도록
고치자 곧바로 `test_dead_board_isolation` 이 실패했다. **seam 이 소비하는 시간도 계약의 일부다.**

> **발견된 버그 — `SCHED_RETRY_BACKOFF_MSEC` 굶주림**<br>
> 이 값이 `RS485_ACK_TIMEOUT_MSEC` 와 같으면(둘 다 100ms) 실패 중인 DANGER 채널이 둘 이상일 때
> 서로 번갈아 도는 사이에 각자의 백오프가 저절로 지나가, 우선순위 패스가 영영 양보하지 않는다.
> 살아 있는 채널이 굶는다 -- 백오프가 막으려던 바로 그 고장이다.<br>
> 조건: 실패 중인 DANGER 채널 K개일 때 한 바퀴에 `(K-1) * (TX + ACK 타임아웃)` 이 걸리므로,
> 백오프가 그보다 짧으면 발생. 한 보드(2채널)가 죽고 둘 다 DANGER 면 K=2 로 실제 발생 가능한 조합이다.<br>
> 조치: `SCHED_RETRY_BACKOFF_MSEC` 를 500ms 로. 되돌리면 이 테스트가 실패한다(회귀 검사).<br>
> 영향: 100ms 일 때 고장 중 DANGER 지연이 **1765ms**, 500ms 일 때 **218ms**.

### 리프레시가 유일한 복구 경로다 (Slave 에 failsafe 가 없다)

Slave 는 링크가 끊겨도 출력을 건드리지 않고 **마지막 상태를 그대로 유지한다**(fail-loud).
"일정 시간 뒤 소등"도 검토했으나 채택하지 않았다 -- 진짜 위험이 진행 중인데 선이 끊기면 경보까지
사라지기 때문이다. 줄 조명은 WS2812 라 색을 래치하므로 회선이 조용해져도 꺼지지 않는다
(NONE 이면 초록이 계속 켜져 있다).

대가는 명확하다: **어긋난 Slave 를 되돌리는 경로가 Master 의 주기 리프레시 하나뿐이다.**
Slave 가 리셋되든 프레임을 놓치든, 상태를 다시 맞춰 주는 것은 여기밖에 없다.
그래서 리프레시가 실제로 도는지가 곧 이 시스템의 복구 능력이다.

`test_refresh_period_guarantee` 가 이것을 지킨다:

- 최악 조건(보드 한 대 사망 + 랜덤 부하)에서 살아 있는 채널의 최대 공백을 잰다 → **2128ms**
- 상한은 `SCHED_REFRESH_MSEC * 2` = 4000ms. 재시도가 끼어들어 한 주기쯤 밀리는 것은 정상이지만
  그 이상 벌어지면 리프레시가 굶고 있는 것이다
- `SCHED_RETRY_BACKOFF_MSEC` 를 잘못 줄이면 이 값이 먼저 터지므로 굶주림 회귀 검사를 겸한다

## 1.5층 — 반응 지연 상한

경보 장비이므로 "언젠가 켜진다"가 아니라 "최악 몇 ms 안에 켜진다"를 숫자로 못박는다.
육안으로는 20ms 와 80ms 를 구분할 수 없어 **실기 관찰로는 절대 얻을 수 없는 값**이다.

| 조건 | 전체 | DANGER | 상한 |
|---|---|---|---|
| 정상 | 48ms | 30ms | 80 / 60ms |
| 보드 한 대 사망 | 270ms | 218ms | 600 / 400ms |

`lat_danger <= lat_any` 도 함께 검사한다 -- DANGER 가 전체 최댓값보다 느리면 우선순위 패스가
duty 를 못 하고 있다는 뜻이다.

같은 계측이 펌웨어에도 들어가 있어 실기 `[stat]` 의 `lat_max` / `lat_dgr` 로 실물 값을 볼 수 있다.
호스트 상한과 실기 값을 나란히 두면 모델이 실물과 얼마나 맞는지도 함께 확인된다.

## 2층 — 굽되 Slave 없이

`rs485_send()` 자리를 UART 로그로 바꿔 스케줄러만 돌린다. 여기서만 나오는 것들:

- **틱 주기 실측** — `sched_task` 진입마다 GPIO 토글하고 로직 애널라이저로 20ms인지 본다.
  `osDelayUntil` 기준선이 밀리면 1층에서는 절대 안 보인다.
- **스택** — `[stack]` 줄에 태스크별 남은 바이트가 5초마다 나온다.
  100바이트 아래로 내려간 태스크가 있으면 그 태스크의 `stack_size` 를 키운다.
- **카운터** — `[stat]` 에 `retry` / `refresh` / `lat_max` / `lat_dgr` 이 나오므로
  3층에서 눈으로 세지 않아도 된다.

## 3층 — 실기 합격 기준

**테스트하기 전에 문장으로 적어 두고** 그것만 본다. 애매하게 "잘 도는지 본다"로 하면 통과 여부를 못 정한다.
현재 기준:

- Slave 전원을 뽑았다 꽂으면 Master가 **RPi 개입 없이** 스스로 상태를 맞춘다(`SCHED_REFRESH_MSEC` 안).
- RPi가 DANGER를 연속으로 밀어도 깜빡임이 밀리거나 몰아서 재생되지 않는다.
- Slave 한 대가 죽어 있는 동안 나머지 Slave의 채널이 계속 갱신된다.
- 릴레이·부저·NeoPixel 표시가 서로 어긋나지 않는다.

## 스케줄러 규칙을 추가할 때 체크리스트

1. 새 규칙이 **기존 규칙보다 먼저 나갈 수 있는가?** → 우선순위 역전 테스트를 1층에 추가한다.
2. 새 규칙이 어떤 채널을 **영영 못 고르게 만들 수 있는가?** → 굶주림 테스트를 추가한다.
   (`SCHED_RETRY_BACKOFF_MSEC`가 정확히 이 이유로 필수였다.)
3. 시간 비교를 새로 썼는가? → **부호 없는 뺄셈**인지 확인하고 틱 접힘 테스트에 케이스를 넣는다.
4. 하드웨어 없이 못 도는 코드가 규칙 안에 섞였는가? → 규칙 밖으로 뺀다. `.inc`가 호스트에서
   컴파일되지 않게 되는 순간 1층 전체가 죽는다.
