## 1주차 — 베어메탈 기초 (마이크로컨트롤러가 어떻게 도는가)

RTOS는 아직 없다고 생각하고 본다.

### 1-1. 클럭 (반나절)
**개념**: MCU는 외부/내부 발진기 → PLL로 체배 → SYSCLK → 버스별 분주(AHB/APB1/APB2).
Flash가 CPU보다 느려서 대기 사이클(latency)이 필요하다는 게 핵심.

**코드**: `main.c`의 `SystemClock_Config()` (1460줄)
```c
RCC_OscInitStruct.PLL.PLLSource = RCC_PLLSOURCE_HSI;  // 내부 16MHz
PLLM = 16; PLLN = 336; PLLP = DIV4;                    // 16/16*336/4 = 84MHz
APB1CLKDivider = RCC_HCLK_DIV2;                        // 42MHz
APB2CLKDivider = RCC_HCLK_DIV1;                        // 84MHz
HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_2);
```
**직접 계산해보기**: 16MHz ÷ 16 × 336 ÷ 4 = **84MHz**. F401RE 최대 클럭이 84MHz라 딱 맞다.

**실습**: `.ioc` 파일을 CubeMX로 열어 Clock Configuration 탭을 눈으로 확인. (파일은 저장하지 말 것 — 코드 재생성되면 USER CODE 밖이 날아간다)

**면접 포인트**: "왜 HSI(내부)를 쓰나?" → Nucleo는 ST-Link의 MCO로 HSE를 받을 수 있지만, 이 프로젝트는 UART 115200 정도의 정밀도만 필요해서 내부 RC로 충분. 정밀 타이밍(CAN, USB)이면 HSE 필수.

### 1-2. GPIO (반나절)
**개념**: 입력/출력/AF(대체기능)/아날로그, Push-Pull vs Open-Drain, Pull-up/down, Speed.

**코드**: `main.c`의 `rs485_de_init()` (778줄)
```c
__HAL_RCC_GPIOA_CLK_ENABLE();          // ← 클럭부터. 안 켜면 레지스터 써도 반영 안 됨
GPIO_InitStruct.Mode = GPIO_MODE_OUTPUT_PP;
GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_VERY_HIGH;
```
그리고 `MX_GPIO_Init()`에서 LD2(PA5), B1 버튼(PC13) 설정.

**실습**: `StartDefaultTask` 안의 LD2 깜빡임 주기를 바꿔서 굽기. `LD2_BLINK_ALIVE_MSEC`(236줄) 값 변경.

**면접 포인트**: "RS485_DE 핀에 왜 VERY_HIGH speed를 줬나?" → DE는 송신 직전/직후 수십 ns 안에 전환돼야 버스 충돌이나 마지막 비트 잘림이 안 난다. 슬루레이트가 느리면 그 창을 놓친다.

### 1-3. UART (1.5일) ★ 이 프로젝트의 심장
**개념**:
- 비동기 직렬. 클럭선 없이 **양쪽이 보드레이트를 미리 약속**한다
- 프레임 = Start(1) + Data(8) + Parity(0) + Stop(1) = 10비트 → 115200bps면 **1바이트 ≈ 87µs**
- 이 87µs가 이 프로젝트 전체 설계의 근거다 (ISR 예산)

**코드**:
- `MX_USART1_UART_Init()`, `MX_USART2_UART_Init()` — CubeMX 생성분
- `rpi_uart_init()` (542줄) — USART6를 손으로 초기화 (CubeMX 밖에서)
- `HAL_UART_MspInit()` in `stm32f4xx_hal_msp.c` — 핀 AF 매핑 + NVIC

**이 프로젝트의 UART 3개, 각각 왜 있나** (외워둘 것):

| UART | 상대 | 용도 | 형식 |
|---|---|---|---|
| USART2 | PC (ST-Link VCP) | 디버그 로그 출력 전용 | ASCII, 115200 |
| USART6 | Raspberry Pi | 관제 서버와 양방향 | **바이너리** 27B 하행 / 19B 상행 |
| USART1 | RS-485 버스 (Slave ×2) | 명령 송신 + ACK 수신 | **ASCII** 고정 9자 |

**실습**: `dbg_print("hello\n")`를 `main()`에 넣고 굽어서 터미널에 뜨는지 확인.

### 1-4. 인터럽트 / NVIC (1.5일) ★★ 면접 최빈출
**개념**:
- 폴링 vs 인터럽트 vs DMA
- NVIC 우선순위: **숫자가 작을수록 높은 우선순위** (Cortex-M 공통 함정)
- ISR은 짧아야 한다. 왜? → 다음 인터럽트를 놓치니까
- **오버런(ORE)**: RX 버퍼(F4는 1바이트, FIFO 없음)를 비우기 전에 다음 바이트가 오면 발생

**코드**: `HAL_UART_RxCpltCallback()` (999줄) — 이 프로젝트에서 가장 중요한 함수 중 하나
```c
if (huart->Instance == USART6) {
    osMessageQueuePut(rpi_rx_queue, &rpi_rx_byte, 0U, 0U);  // 큐에 넣기만
    HAL_UART_Receive_IT(huart, &rpi_rx_byte, 1U);           // ← 즉시 재무장
}
```
주석에 설계 이유가 다 적혀 있다: **"체크섬 계산(24바이트 XOR)까지 ISR에 넣으면 87µs 예산을 갉아먹으므로, 큐에 넣는 것만 하고 상태머신은 rx_task가 돌린다."**

그런데 USART1(ACK)은 ISR에서 **줄 조립까지** 한다 (`ack_feed_byte`). 왜 다른가?
→ ACK는 최대 11바이트라 조립이 87µs 안에 끝나고, ACK를 기다리는 sched_task가 결과를 바로 큐에서 꺼내야 하기 때문.

`HAL_UART_ErrorCallback()` (1032줄)도 반드시 읽을 것:
> "재무장하지 않으면 오류 한 번으로 수신이 영구히 멈춘다."

**실습**:
1. `stm32f4xx_it.c`에서 `USART1_IRQHandler` → `HAL_UART_IRQHandler` → `HAL_UART_RxCpltCallback` 호출 사슬을 직접 따라가 보기
2. 일부러 `HAL_UART_Receive_IT` 재무장 줄을 주석 처리하고 굽어서 — 로그가 한 번만 찍히고 멈추는 것 관찰 → 되돌리기

**면접 포인트**: NVIC 우선순위 5가 여러 곳에 나온다(`USART1_IRQn`, `USART6_IRQn`). 이건 `FreeRTOSConfig.h`의 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`와 짝이다. **5보다 우선순위가 높은(숫자가 작은) ISR에서는 FreeRTOS API를 절대 부르면 안 된다.** 이 프로젝트 ISR이 `osMessageQueuePut`을 부르므로 정확히 5에 맞춰 놓은 것. ← 이거 아는 신입 거의 없다.

**1주차 체크**
- [ ] 84MHz가 어떻게 나오는지 계산해서 설명한다
- [ ] 115200bps에서 1바이트가 87µs인 이유를 유도한다
- [ ] "ISR을 짧게" 원칙이 이 코드 어디에 어떻게 적용됐는지 두 곳(USART6 vs USART1)을 비교해 설명한다
- [ ] NVIC 우선순위 5와 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`의 관계를 설명한다

## 2주차 — FreeRTOS (일이 여러 개 동시에 도는 법)

### 2-1. 왜 RTOS인가 (반나절)
슈퍼루프(`while(1)`)로 이걸 짜면:
- RS-485 송신이 블로킹 1ms 도는 동안 RPi 하행 바이트를 놓친다
- HEARTBEAT 500ms 주기가 하행 처리에 밀린다 → RPi가 Master를 dead로 오판

**코드**: `main.c` 1050줄 근처의 태스크 구성도 주석 — 왜 나눴는지가 4줄로 정리돼 있다.

### 2-2. 태스크 / 스케줄링 (1일)
**개념**: 태스크 상태(Running/Ready/Blocked/Suspended), 선점형 스케줄링, 우선순위, 각 태스크는 **자기 스택을 따로 갖는다**.

**코드**: `main.c` 441~468줄
| 태스크 | 우선순위 | 스택 | 역할 |
|---|---|---|---|
| `rxTask` | AboveNormal | 1024B | 하행 바이트 → 프레임 조립 |
| `ctrlTask` | Normal | 1024B | 이벤트 접수 → `desired`만 기록 |
| `schedTask` | Normal | 1024B | **유일한 RS-485 송신자.** 20ms 틱 |
| `txTask` | Normal | 768B | 상행 송신 (USART6 송신자 단일화) |
| `hbTask` | BelowNormal | 768B | 500ms HEARTBEAT |
| `defaultTask` | Normal | - | 감시·로그 |

**우선순위를 왜 이렇게 줬나** (주석에 있음):
- `rxTask`가 제일 높다 → 바이트 큐가 먼저 비어야 오버런이 안 난다
- `ctrlTask`와 `schedTask`가 같다 → 접수와 실행 중 어느 쪽도 상대를 굶기면 안 된다
- `hbTask`가 제일 낮다 → 주기 보고라 밀려도 되지만, 밀린 만큼 dead 판정에 가까워진다

**실습**: `[stack]` 로그를 보고 각 태스크 스택 여유 확인 (`uxTaskGetStackHighWaterMark` 사용, 643줄).

**개선 과제 (직접 해볼 것)**: 지금 `FreeRTOSConfig.h`에는 `configCHECK_FOR_STACK_OVERFLOW`가 **정의돼 있지 않다**(= 0, 꺼짐). 이걸 `2`로 켜고 `vApplicationStackOverflowHook()`을 구현한 뒤, `rxTask` 스택을 `64*4`로 줄여 굽고 훅이 걸리는지 확인해 보자. 확인 후 되돌린다.
→ **면접용**: "왜 켰나?" 스택 오버플로는 조용히 옆 태스크 메모리를 망가뜨려서, 검출이 없으면 원인 추적이 거의 불가능하다. 방식 1은 스택 포인터 범위만 보고(싸다), 방식 2는 스택 끝의 매직 패턴 훼손까지 본다(느리지만 정확).

### 2-3. 태스크 간 통신 — 큐 (1일) ★
**개념**: 큐는 **값 복사**로 전달한다(포인터 공유가 아니라). 그래서 소유권 문제가 사라진다.
큐 4개:
```c
rpi_rx_queue   (깊이 128, uint8_t)         ISR      → rxTask
cmd_queue      (깊이 8, veda_risk_event_t) rxTask   → ctrlTask
ack_queue      (깊이 8, rs485_ack_t)       ISR      → schedTask
uplink_queue   (깊이 12)                   여러 곳  → txTask
```

**꼭 이해할 패턴**: 큐가 가득 차면 이 코드는 **버리고 카운터를 올린다**. 블로킹하지 않는다.
```c
if (osMessageQueuePut(cmd_queue, &event, 0U, 0U) != osOK) { ++stat_cmd_dropped; }
```
왜? → `enqueue_uplink` 주석: *"여기서 블로킹하면 ctrl_task가 하행 처리를 멈추게 된다 — 경광등 반응 지연이 더 나쁘다."*
**실시간 시스템의 전형적 트레이드오프**다. 면접에서 이 문장 그대로 쓸 수 있다.

### 2-4. 동기화 — 뮤텍스 (반나절)
**코드**: `channel_status_mutex`. `channel_status[]`는 schedTask가 쓰고 txTask/hbTask가 읽으므로 보호가 필요.
```c
osMutexAcquire(channel_status_mutex, osWaitForever);
channel_status[channel_index] = next;
osMutexRelease(channel_status_mutex);
```
**개념**: 뮤텍스 vs 세마포어 차이, 우선순위 역전과 우선순위 상속.
**주의**: ISR에서는 뮤텍스를 못 쓴다 → 그래서 ISR은 큐만 쓴다.

### 2-5. 시간 (반나절)
- `osDelay()` vs `osDelayUntil()` — 후자가 **주기 드리프트를 막는다**
- `schedTask`가 `osDelayUntil`을 쓰는 이유: 20ms 틱이 정확해야 모든 지연 계산의 전제가 선다
- **틱 랩어라운드**: `osKernelGetTickCount()`는 uint32라 약 49일 만에 감긴다.
  이 코드는 전부 **부호 없는 뺄셈**으로 경과를 잰다 → 감겨도 정확하다.
  ```c
  const uint32_t idle = osKernelGetTickCount() - channel_ctrl[ch].last_tx_tick;
  ```
  ← 면접 단골. `if (now > last + TIMEOUT)` 로 쓰면 랩어라운드에서 터진다.

**2주차 체크**
- [ ] 태스크 5개의 이름·우선순위·역할을 안 보고 말한다
- [ ] "왜 슈퍼루프로 안 짰나"를 구체적 실패 시나리오 2개로 답한다
- [ ] 큐가 가득 찼을 때 블로킹하지 않고 버리는 이유를 설명한다
- [ ] 틱 랩어라운드 안전한 시간 비교 코드를 칠판에 쓴다

## 3주차 — 통신 프로토콜과 이 시스템의 설계 ★★ 면접의 90%

### 3-1. 프레이밍과 체크섬 (1일)
**개념**: 직렬 스트림에는 "메시지 경계"가 없다. 그래서 필요한 것:
STX/ETX(구분), 길이 또는 고정크기, 체크섬(무결성), 재동기화(깨졌을 때 복구).

**코드**: `Core/Inc/driver_protocol.h` — **RPi(C++)와 STM32(C)가 같은 헤더를 include한다**
```c
#pragma pack(push, 1)   // 컴파일러 자동 패딩 끄기
typedef struct {
    uint8_t channel_id;   uint8_t risk_level;   uint8_t reserved0[6];  // ← 수동 정렬
    int64_t timestamp_ms;
    uint16_t dist_mm;     uint8_t reserved1[6];
} veda_risk_event_t;      // sizeof == 24
```
그리고 `main.c` 262줄:
```c
_Static_assert(sizeof(veda_risk_event_t) == 24, "veda_risk_event_t must be 24 bytes");
```
**이 두 줄이 면접에서 아주 좋다**: 구조체 크기가 어긋나면 **컴파일이 안 된다**. 런타임 미스터리 버그를 컴파일 타임 오류로 끌어올린 것.

**꼭 짚을 것**: `#pragma pack(1)`으로 패딩을 껐는데도 `reserved[6]`을 손으로 넣은 이유는?
→ 패킹만 하면 `int64_t`가 8바이트 경계에 안 맞아 **비정렬 접근**이 된다. Cortex-M4는 대부분 허용하지만 느리고, 아키텍처에 따라 폴트가 난다. 그래서 정렬은 손으로 보장.

**체크섬**: XOR (`veda_checksum`). 양쪽이 **같은 inline 함수를 공유**해서 구현이 갈라지는 걸 원천 차단.
> 한계도 알아둘 것: XOR은 비트 순서 바뀜/짝수 개 오류를 못 잡는다. CRC-8/16이 더 강하다. 면접에서 "왜 CRC가 아니라 XOR?"이 나오면 → "짧은 유선 링크에 계산 비용이 싸서. 링크가 길거나 노이즈가 심하면 CRC-16으로 올려야 한다"가 정답.

**코드**: `downlink_feed_byte()` (945줄) — 바이트 하나씩 먹는 **상태머신**. `DL_WAIT_START` → payload → checksum → end.
이 패턴(1바이트 피드 상태머신)은 임베디드 실무에서 계속 쓴다. **반드시 손으로 다시 짜볼 것.**

### 3-2. RS-485 (1일) ★
**개념**:
- UART는 **논리 레벨**(0/3.3V), RS-485는 **차동 신호**(A/B 두 선의 전압 차) → 노이즈 내성, 1200m
- **반이중(half-duplex)**: 한 쌍의 선을 송/수신이 나눠 쓴다 → 누가 언제 말할지 정해야 한다
- **DE(Driver Enable)**: 송신 전에 올리고, 송신 완료 후 내린다. 안 내리면 버스를 점유해 다른 노드가 못 말한다
- **멀티드롭**: 여러 노드가 한 버스에 → 프레임 안에 **주소**가 필요

**코드**: `send_channel_command()` (823줄)
```c
HAL_GPIO_WritePin(RS485_DE_GPIO_Port, RS485_DE_Pin, GPIO_PIN_SET);   // 송신 모드
status = HAL_UART_Transmit(&huart1, frame, length, RS485_TX_TIMEOUT_MSEC);  // 블로킹
HAL_GPIO_WritePin(RS485_DE_GPIO_Port, RS485_DE_Pin, GPIO_PIN_RESET); // 수신 모드
```
주석이 핵심을 짚는다: *"HAL_UART_Transmit()은 마지막 바이트의 TC(전송 완료)까지 기다린 뒤 반환하므로 여기서 바로 내려도 마지막 비트가 잘리지 않는다."*
> **면접 함정**: `HAL_UART_Transmit_IT`(비블로킹)로 바꾸면 이 코드는 **깨진다**. 함수가 즉시 반환하므로 DE를 너무 일찍 내려 마지막 바이트가 잘린다. 그럴 땐 `HAL_UART_TxCpltCallback`에서 내려야 한다. ← 이 질문 실제로 자주 나온다.

**프레임 형식**: `"S<슬레이브>:CH<채널>:R<위험도>\n"` — 항상 9자 고정
```
index 0 -> "S1:CH1"   index 1 -> "S1:CH2"
index 2 -> "S2:CH3"   index 3 -> "S2:CH4"
```
주석의 실패담이 좋은 면접 소재다: *"보드당 1채널이던 시절에는 슬레이브 번호와 채널 번호가 같아서 하나로 계산했는데, 그 코드를 그대로 두면 CH3이 S3(존재하지 않는 보드)으로 나가 조용히 사라진다."*

또 하나: 옛 규약이 `":ON"/":OFF"`였는데 그러면 **WARNING과 DANGER가 회선 위에서 같은 값으로 합쳐져** Slave가 구분할 수 없었다. → **프로토콜 설계에서 정보를 잃으면 하위에서 복구 불가**라는 교훈.

**실습**: 오실로스코프 없으면 → Slave 보드의 USART2 로그(`RX "..." -> 판정`)로 회선 내용을 확인.

### 3-3. ACK / 재시도 / 스케줄러 (2일) ★★★ 이 프로젝트의 정수
**핵심 설계: 접수와 실행의 분리**
```
ctrl_task : 검증된 이벤트를 받아 desired(원하는 등급)만 적는다. 송신 안 한다
sched_task: 유일한 송신자. 20ms마다 desired != applied 인 채널 하나를 골라 보내고 ACK를 기다린다
```
**ACK를 받아야만 `applied`를 갱신** → 실패하면 `desired != applied`가 그대로 남아 **다음 틱에 자동 재시도**된다.
> **재시도 큐도 타이머도 따로 필요 없다.** 이게 이 설계의 가장 우아한 부분이고, 면접에서 반드시 말할 것.

**읽는 순서**:
1. `Core/Inc/sched_select.inc` — `pick_pending()`: 누구를 고르나
2. `Core/Inc/sched_dispatch.inc` — `dispatch_channel()` / `sched_tick()`: 고른 뒤 상태 전이
3. `Core/Inc/ack_parse.inc` — ACK 줄 조립·해석 (ISR 문맥)
4. `Core/Inc/ack_match.inc` — 늦은/남의 ACK 대조

**`sched_tick()`의 2패스 구조**:
```c
ch = pick_pending(1U);   // 1차: DANGER만  (경보를 켜는 일이 끄는 일보다 급하다)
if (ch == NO_CHANNEL) ch = pick_pending(0U);   // 2차: 나머지 라운드로빈
```
두 패스가 **같은 커서(`sched_cursor`)를 공유**해서 굶주림(starvation)을 막는다.

**`pick_pending()`에서 반드시 이해할 3가지**:
1. **커서에서 시작해 한 바퀴만 돈다** — 매번 0부터 훑으면 CH1에 이벤트가 계속 들어올 때 CH4가 영영 밀린다
2. **백오프**: 방금 실패한 채널은 `SCHED_RETRY_BACKOFF_MSEC`(500ms) 동안 양보. 없으면 죽은 Slave 하나가 우선순위 패스를 독점
3. **주기 리프레시**: 값이 맞아도 `SCHED_REFRESH_MSEC`(2000ms) 지나면 다시 보낸다 → Slave가 리셋되거나 프레임을 놓쳐도 여기서 복구

**절대 잊으면 안 되는 상수 관계** (CLAUDE.md에 경고로 적혀 있음):
```
SCHED_RETRY_BACKOFF_MSEC (500ms)  >>  RS485_ACK_TIMEOUT_MSEC (100ms)
```
같으면(둘 다 100ms) 실패 중인 DANGER 채널이 둘 이상일 때 서로 번갈아 도는 사이에 각자 백오프가 저절로 지나가, **우선순위 패스가 영영 양보하지 않아 살아 있는 채널이 굶는다.**
→ 실제로 `test_sched_loop`가 이 버그를 잡았다. **면접 최고의 소재.**

**`ack_match.inc` — 늦은 ACK 문제**:
앞 명령에 대한 늦은 ACK가 남아 있으면 이번 명령의 확인으로 오인된다. 그래서 보내기 전에 `drain_ack_queue()`로 큐를 비운다.
→ **에코 처리**: 자동 방향 전환 트랜시버는 자기 송신을 되울리므로, ACK 파서가 첫 글자 `'S'`(우리 명령)를 조용히 버린다. `ack_bad`로 세지 않는다 — 세면 명령마다 카운터가 올라 진짜 오류를 가린다.

**실습 (가장 중요)**:
1. Slave #2의 전원을 뽑고 Master `[stat]` 관찰 → `ack_to`, `retry` 증가, `lat_dgr`이 36ms → 218ms로 뛰는 것 확인
2. `SCHED_RETRY_BACKOFF_MSEC`을 100으로 되돌려 굽고 → 굶주림 관찰 → 되돌리기
3. `SCHED_REFRESH_MSEC`을 30000으로 늘리고 → Slave를 리셋했을 때 복구가 얼마나 늦는지 관찰 → 되돌리기

**3주차 체크**
- [ ] "접수와 실행의 분리"를 30초 안에 설명한다
- [ ] 재시도 큐 없이 재시도가 성립하는 이유를 설명한다
- [ ] DE 핀 타이밍과 `HAL_UART_Transmit` vs `_IT`의 차이를 설명한다
- [ ] `_Static_assert`로 구조체 크기를 못박은 이유를 설명한다
- [ ] backoff > ack_timeout 이어야 하는 이유를 굶주림 시나리오로 설명한다

## 4주차 — 검증, 계측, 그리고 면접 준비

### 4-1. 호스트 테스트 (1.5일) ★★ 차별화 포인트
임베디드 지원자 대부분이 "보드에 굽고 눈으로 봤다"까지다. **PC에서 펌웨어 로직을 테스트했다**는 건 크게 다르다.

**핵심 아이디어**: `.inc` 파일은 컴파일 단위가 아니라 `main.c`가 `#include`하는 조각이다.
**추상화가 아니라 검증이 목적** — 호스트 테스트가 **같은 파일을 포함**해서 실기와 갈라지지 않게 한다.

```sh
cd tools
gcc -Wall -Wextra -I../Core/Inc test_sched_select.c -o test_sched_select && ./test_sched_select
gcc -Wall -Wextra -I../Core/Inc test_ack_parse.c    -o test_ack_parse    && ./test_ack_parse
gcc -Wall -Wextra -I../Core/Inc test_ack_match.c    -o test_ack_match    && ./test_ack_match
gcc -Wall -Wextra -I../Core/Inc test_sched_loop.c   -o test_sched_loop   && ./test_sched_loop
```

**`test_sched_loop.c`가 특히 볼 만하다**: 가짜 RPi가 33ms마다 랜덤 명령을 던지고 가짜 Slave가 응답하는 **닫힌 루프 시뮬레이션**. 가상 시계라 300시드 × 30초를 0.1초에 돈다.

**seam(이음매) 개념** — `sched_dispatch.inc` 상단 주석 참고. 하드웨어/RTOS와 닿는 경계가 딱 6개:
`send_channel_command` / `wait_for_slave_ack` / `drain_ack_queue` / `enqueue_uplink` / `risk_to_status` / `pick_pending`
테스트는 **그 6개만 가짜로 갈아끼우고** 상태 전이 로직은 실기와 100% 같은 것을 돌린다.

**교훈 하나 (면접용)**: *"가짜 seam은 '시간'도 모델링해야 한다. 가짜 ACK가 즉답하면 실패한 ACK가 공짜가 되어 실기에서 가장 크게 밀리는 구간이 사라진다. 실제로 이것 때문에 굶주림 버그를 놓치고 있었다."*

### 4-2. 뮤테이션 테스트 (반나절) ★ 여기까지 하면 상위 1%
```sh

```
펌웨어를 **일부러 망가뜨린 사본**으로 테스트를 돌린다. "전부 통과"가 코드가 옳은 것인지 **테스트가 아무것도 안 보는 것**인지 가려 준다.
