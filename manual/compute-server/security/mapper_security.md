## 1. 위협 모델 (Threat Model)

`AffineImageCoordinateMapper` 는 **순수 수치 계산 계층**이다. I/O 도, 소유한 동적 자료구조도, 파싱도 없다. 위협은 두 갈래로 들어온다.

| 출처 | 통제 주체 | 위협 |
|------|-----------|------|
| **입력 bbox** (`DetectedObject::box`) | **카메라(신뢰 불가)** | NaN/Inf, 극단값, 퇴화 박스 → 발산·비유한 좌표가 앱으로 전달 |
| **매핑 파라미터** (`scale`/`offset`) | 운영자 `config.json` | 0·음수 스케일, 비유한 값 → 좌표 뒤집기·전량 소실 |

| 위협 범주 | 시나리오 | 성립 여부 |
|-----------|----------|-----------|
| **0 나눗셈 / 발산** | 분모를 0으로 유도 | ✅ **구조적 불가 — 나눗셈이 없음** |
| **NaN/Inf 전파** | 비유한 bbox 를 앱으로 흘림 | ✅ 차단 |
| **좌표 뒤집기** | 음수 scale 로 `l > r` 유도 | ✅ 조립 시점 throw |
| **화면 밖 팬텀 블러** | 화면 밖 박스가 가장자리에 달라붙음 | ✅ 차단 |
| **퇴화 박스** | 면적 0 박스를 앱에 전달 | ✅ 제거 |
| OOM / 힙 고갈 | 대량 객체로 할당 폭증 | ✅ **호출당 할당 0** |
| 스택 고갈 | 재귀/대형 지역 배열 | ✅ 구조적 불가 |
| CPU 고갈 | 대량 객체로 연산 폭증 | ✅ O(N), N ≤ 256 상한 |
| **로그 도배 / 로그 인젝션** | 실패 로그로 디스크·CPU 소모 | ✅ 프레임당 1회, CSV 이스케이프 |

### 실패 방향 분석

이 계층의 실패는 **"블러가 걸리지 않는다"** 로 나타난다. 이는 안전 판정이 아니라 **개인정보 보호**의 문제다.

| 방향 | 결과 | 평가 |
|------|------|------|
| **과소 검출** (박스를 제거) | 얼굴/번호판이 노출됨 | ⚠️ **개인정보 노출** |
| **과대 검출** (엉뚱한 곳을 블러) | 영상 일부가 불필요하게 가려짐 | 시인성 저하 (경미) |

> **⚠️ risk 경로와 실패 방향이 정반대다.** risk 경로는 "확신할 수 없으면 폐기"가 안전하지만 (틀린 좌표로 오경보를 내느니), blur 경로는 **폐기가 곧 노출**이다. 그래서 가시성 판정이 의도적으로 **관대**(`r>0 && l<1 && b>0 && t<1` — 조금이라도 겹치면 살림)하고, 전량 필터링은 명시적 오류 로그로 즉시 드러나게 했다.

## 2. 아핀 연산 안전성 (Affine Math & Bounds)

### 2.1 ✅ 0 나눗셈 — 구조적으로 성립 불가

```
l' = l·scaleX + offsetX      r' = r·scaleX + offsetX
t' = t·scaleY + offsetY      b' = b·scaleY + offsetY
```

**곱셈과 덧셈만** 수행한다. 나눗셈도, 역행렬도, 입력 의존 분모도 없다. `HomographyTransform` 에서 가장 위험했던 원근 나눗셈이 **이 계층에는 아예 존재하지 않는다.**

발산도 마찬가지다. 유한한 입력 × 유한한 scale + 유한한 offset 은 `double` 범위를 넘지 않는 한 유한하다.

### 2.2 ✅ NaN / Inf 전파 — 이중 방어

**파라미터 측**: 생성자가 scale/offset 4개의 유한성을 검사해 하나라도 비유한이면 **throw** 한다.

**입력 측**: 매핑 결과 4좌표를 `isFinite` 로 검사해 실패하면 **해당 객체를 제거**한다.

```cpp
if (!isFinite(mapped.l) || !isFinite(mapped.r) || !isFinite(mapped.t) || !isFinite(mapped.b) ||
    !isVisible(mapped)) {
    continue;   // 원소 제거
}
```

> **⚠️ 상류 의존 기록**: 정상 경로에서는 파서의 `isfinite` 검사(W2 패치)가 NaN 좌표 객체를 이미 폐기하므로 여기까지 도달하지 않는다. 이 계층의 검사는 **두 번째 방어선**이다. 파서 검사가 회귀해도 비유한 좌표가 앱으로 나가지 않는다.

### 2.3 ✅ 스케일 부호·크기 — 조립 시점 fail-fast

```cpp
if (!isFinite(scaleX_) || !isFinite(scaleY_) || !isFinite(offsetX_) || !isFinite(offsetY_) ||
    scaleX_ <= 0.0 || scaleY_ <= 0.0) {
    throw std::invalid_argument("image coordinate mapper requires finite positive scales");
}
```

| 거부 대상 | 거부 이유 |
|-----------|-----------|
| `scale < 0` | 좌표계가 뒤집혀 `l > r`, `t > b` 가 된다. 아핀 변환은 순서를 보존하지 않으므로 이후 모든 판정이 무의미해진다 |
| `scale == 0` | 모든 박스가 한 점으로 붕괴 → 전량 제거 → **블러가 완전히 사라진다.** |
| `NaN` / `Inf` | 모든 박스가 비유한 → 전량 제거 |

`main` 이 이 예외를 잡아 **프로세스를 종료**한다. 이는 "조용히 틀린 출력을 내보내느니 즉시 죽는 편이 안전하다" 규약과 일치하며, 특히 blur 경로에서는 **"블러가 조용히 사라진 상태로 서비스가 계속 도는 것"** 이 최악의 결과이므로 타당하다.

> **ℹ️ 상한은 없다.** `scaleX = 1e9` 같은 값은 허용된다. 이 경우 모든 박스가 가시성 판정에서 걸러지고 전량 필터링 경고가 뜬다. — **조용히 틀리지 않고 시끄럽게 비어 있으므로** 별도 상한을 두지 않았다.

### 2.4 ✅ 범위 검사 — 순서가 방어의 핵심

```cpp
if (!isFinite(4개) || !isVisible(mapped)) continue;   // ② 먼저 가시성 판정
clampToOutput(mapped);                                // ③ 그 다음 클램프
if (mapped.r <= mapped.l || mapped.b <= mapped.t) continue;   // ④ 퇴화 제거
```

```cpp
bool isVisible(const domain::NormBox& box) {
    return box.r > 0.0 && box.l < 1.0 && box.b > 0.0 && box.t < 1.0;
}
```

**②를 ③보다 먼저 하는 것이 이 계층의 유일한 순서 의존성이자 핵심 방어다.**

클램프를 먼저 하면, 예컨대 `l = 3.2, r = 3.8` (완전히 화면 오른쪽 밖) 인 박스가 `l = 1.0, r = 1.0` 으로 접히고 — 만약 퇴화 검사마저 통과하는 경계 조건이라면 — **화면 가장자리에 달라붙은 존재하지 않는 블러**가 그려진다. 가시성을 먼저 판정하면 이 박스는 클램프 이전에 제거된다.

역으로 `isVisible` 이 **관대**(경계에 조금이라도 걸치면 통과)한 것도 의도적이다. 프레임 밖으로 절반 나간 얼굴은 **남은 절반이라도 가려야** 하기 때문이다.

### 2.5 ✅ 퇴화 박스 제거

클램프 결과 면적이 0이 된 박스(`r <= l || b <= t`)를 제거한다. 면적 0 박스는 앱에서 렌더링 오류나 0-division 을 유발할 수 있는 값이며, 실질적 블러 효과도 없다. **앱 측 방어에 의존하지 않고 발신 측에서 차단한다.**

### 2.6 ✅ 경계 플래그 오염 차단 (설계 방어)

`touchesBorder` / `bottomTruncated` 는 risk 경로가 쓰는 값이며 **메타데이터 좌표계 기준으로만** 의미가 있다. 이 계층은 읽지도 쓰지도 않는다.

```cpp
object.box = mapped;
// touchesBorder/bottomTruncated 는 건드리지 않음
```

클램프 이후에 재판정하면 **"앱 화면 기준 경계"** 라는 다른 의미가 같은 필드에 섞인다. 그러면 `RiskEdgePolicy::DropBottomTruncated` 가 **blur 좌표계 기준으로 risk 객체를 버리는** 결과가 되어, 컴파일 오류도 런타임 오류도 없이 **검출이 조용히 사라진다.** "판정의 단일 소유권"은 이 계층의 명시적 보안 속성이다.

## 3. 메모리 & 스택 안전성

### 3.1 ✅ 호출당 힙 할당 0 — OOM 위험 없음

| 저장소 | 형태 |
|--------|------|
| `AffineImageCoordinateMapper` 멤버 | `double` 4개 — **힙 컨테이너 미소유** |
| 함수 지역 | `NormBox mapped` 1개 + 인덱스 2개 — **O(1)** |
| 작업 대상 벡터 | **호출자 소유** (in-place 축소만 함) |

```cpp
std::size_t writeIdx = 0;
for (...) {
    ...
    if (writeIdx != readIdx) objects[writeIdx] = std::move(object);
    ++writeIdx;
}
objects.resize(writeIdx);   // 축소는 재할당을 유발하지 않음 (capacity 유지)
```

**새 벡터를 만들지 않는다.** 출력 개수는 항상 입력 이하이므로 통과 원소를 앞으로 당긴 뒤 잘라내면 충분하다. `resize` 로 **줄이는 것**은 재할당도 해제도 유발하지 않으므로, 다음 프레임에서 같은 capacity 가 재사용된다.

**검증**: 단위 테스트(`MapperTest`)에서 전역 `operator new` 를 계수해 **64객체 `map()` 호출의 힙 할당 0회**, **전량 필터링 후에도 capacity 보존**을 확인했다.

> 반환값 형태(`std::vector<...> map(...)`)로 "단순화"하면 프레임당 1회의 할당이 되살아난다. `IObjectRouter::route` 의 out-parameter 계약과 같은 이유로 금지된다.

### 3.2 ✅ 스택 오버플로 — 구조적 면역

- **재귀 없음** <br> `map()` 은 단일 평면 루프이고, 헬퍼(`isFinite`, `isVisible`, `clampToOutput`)는 모두 리프 함수다.
- 지역 저장소는 입력 크기와 무관한 **O(1)** — 대형 지역 배열(VLA, `alloca`, 큰 `std::array`)이 없다.
- `ContainmentSanitizer` 의 `std::bitset<256>` 같은 크기 의존 스택 객체조차 없다.

### 3.3 ✅ 로그 경로 — 프레임당 1회, 조기 조립 문제 없음

```cpp
if (inputCount > 0 && writeIdx == 0) {
    logError(kIface, "ch=" + std::to_string(channelId) + " 입력 blur 객체 " +
                     std::to_string(inputCount) + "개가 전부 필터링됨 (scale/offset 설정 확인 필요)");
}
```

- **호출 빈도**: 루프 밖, **프레임당 최대 1회** <br> `HomographyTransform` 의 M1(객체당·프레임당 조립)과 달리 rate-limit 이 필요 없는 수준이다.
- **발생 조건**: 비정상 상황(전량 필터링)에서만 <br> 정상 운영에서는 실행되지 않는다.
- **로그 인젝션**: 메시지에 들어가는 값은 `channelId`(정수)와 `inputCount`(정수)뿐이다. **카메라가 제어하는 문자열이 로그에 들어가는 경로가 없다.** 파서에서 필요했던 `sanitizeForLog` 가 여기서는 불필요하다.
- CSV 필드 이스케이프는 `Logger` 의 `csvEscape` 가 담당하므로 이중 방어도 성립한다.

## 4. 성능 (CPU / FPU)

### 4.1 ✅ 프레임당 O(N), 객체당 상수 비용

| 연산 (객체 1개당) | 횟수 |
|-------------------|------|
| 곱셈 | 4 (l, r, t, b) |
| 덧셈 | 4 |
| **나눗셈** | **0** |
| 비교 (유한성 + 가시성 + 퇴화) | 최대 12 |
| 클램프 | 4 (`std::clamp`) |
| 이동 대입 | 최대 1 (`std::move`, 필터가 걸렸을 때만) |

**중첩 루프가 없다.** `ContainmentSanitizer` 의 O(N²) 쌍 비교와 달리 이 계층은 **단일 순회**다.

| 항목 | 값 |
|------|-----|
| 최악 객체 수 | 256 (파서 상한) — 실제로는 blur 대상(Head/LicensePlate)만이므로 훨씬 적다 |
| 최악 부동소수 연산 | 약 256 × 8 ≈ **2,000 flop** |
| 추정 소요 | 라즈베리파이 기준 **수 마이크로초** |
| 프레임 예산 | 5 fps → **200 ms** |

**➡️ 프레임 예산의 0.01% 미만이다. CPU 고갈 공격이 성립하지 않는다.**

### 4.2 ✅ 분기 예측 친화적

정상 프레임에서는 모든 객체가 필터를 통과하므로 `continue` 분기가 거의 taken 되지 않고, `writeIdx != readIdx` 도 계속 false다. (이동 대입 자체가 생략됨) **정상 경로가 가장 싼 경로**가 되도록 짜인 구조다.

### 4.3 ✅ 스레드 안전

`map()` 은 **`const`이고 가변 상태를 갖지 않는다.** `HomographyTransform::toLocal()` 이 `failureCount_` 때문에 스레드 안전하지 않은 것과 대비된다. 이 계층은 다중 스레드 파이프라인으로 확장하더라도 **락 없이 그대로 공유 가능**하다.

| **A1** | scale 에 **상한이 없다** (`1e9` 허용) | ℹ️ Info | 극단값은 전량 필터링 → 명시적 오류 로그로 드러난다. 조용한 오작동이 아니므로 상한 미도입은 합리적 |
| **A2** | 기본값이 **항등 변환** (`scale=1, offset=0`) | ℹ️ Info | "보정 불필요가 검증된 상태"가 아니라 "보정하지 않은 상태"다. 메타데이터 화각과 송출 화각이 실제로 같은지 확인하지 않으면 블러가 미세하게 빗나갈 수 있다 |
| **A3** | 입력 bbox 자체의 유효성은 검사하지 않는다 | ℹ️ Info | 파서·Sanitizer 가 상류에서 이미 판정한다. 결과 측 검사가 두 번째 방어선 역할을 하므로 중복 검사는 불필요 |

**총평**: `AffineImageCoordinateMapper` 는 **이 코드베이스에서 공격 표면이 가장 좁은 계층**이다. 나눗셈이 없어 `HomographyTransform` 이 3중 관문으로 막아야 했던 위험군(0 분모·지평선·발산·팬텀 좌표)이 **구조적으로 성립하지 않고**, 힙 컨테이너를 소유하지 않아 OOM 도, `const` 라 데이터 경합도 없다.

방어의 실질적 무게는 **파라미터 검증과 필터 순서** 두 곳에 있다. 전자는 "블러가 조용히 사라지는" 최악의 실패를 조립 시점에 잡고, 후자는 화면 밖 박스가 가장자리에 달라붙는 팬텀 블러를 막는다. 이 두 지점만 회귀하지 않으면 이 계층은 안전하다.

**Critical·Warning 결함은 없다.** 지적 사항은 전부 Info 등급이며 조치를 권고하지 않는다.
