## 1. 위협 모델 (Threat Model)

`EuclideanMetric` 은 **순수 수치 계산 계층**이다. I/O도, 소유한 동적 자료구조도, 파싱도,
가변 상태도 없다. 공격 표면은 **입력 좌표값** 하나뿐이다.

| 출처 | 통제 주체 | 위협 |
|------|-----------|------|
| **`p1` / `p2`** (월드 좌표) | 상류 변환 계층 (간접적으로 원격 카메라) | NaN/Inf → 판정 조용한 실패 |
| — | — | 그 외 외부 입력 경로 **없음** |

| 위협 범주 | 시나리오 | 성립 여부 |
|-----------|----------|-----------|
| **NaN/Inf 전파** | 비유한 좌표로 위험 판정 무력화 | ✅ **상류 차단** |
| **0 나눗셈 / 발산** | 분모를 0으로 유도 | ✅ **구조적 불가 — 나눗셈이 없음** |
| **오버플로** | 극단 좌표로 `dx*dx` 폭주 | ✅ 여유 300 자릿수 (2.2) |
| **블로킹 I/O** | 계산 중 파일/네트워크 대기 | ✅ **구조적 불가 — I/O 경로 없음** |
| **OOM / 힙 고갈** | 대량 호출로 할당 폭증 | ✅ **호출당 할당 0** |
| **무한 메모리 증가** | 소비자 정체 시 버퍼 누적 | ✅ **구조적 불가 — 버퍼가 없음** |
| **스택 오버플로** | 재귀·대형 지역 배열 | ✅ 구조적 불가 |
| **CPU 고갈** | 대량 객체로 O(N²) 증폭 | ⚠️ 상한은 있으나 증폭 계수가 큼 |
| **데이터 경합** | 다중 스레드 동시 호출 | ✅ 무상태 `const` |
| **로그 인젝션** | 로그로 디스크·CPU 소모 | ✅ **로그 경로 자체가 없음** |

### 실패 방향 분석

이 계층의 실패는 **"거리가 실제보다 멀게 나온다"** 로 나타난다.

| 방향 | 결과 | 평가 |
|------|------|------|
| **과대 거리** (실제보다 멀다고 판정) | 임계값 미달 → **경보 미발생** | ⚠️ **충돌 위험 — 최악** |
| **과소 거리** (실제보다 가깝다고 판정) | 불필요한 경보 | 오경보 (경미) |

> **⚠️ risk 경로의 실패 방향은 blur 경로와 정반대다.** blur는 "버리면 노출"이지만,
> 거리 계산은 **"멀다고 하면 경보가 안 나간다."** NaN은 모든 비교를 false로 만들어
> 정확히 이 최악 방향으로 실패한다.

## 2. 수치 안전성 (Numerical Safety)

### 2.1 ✅ 0 나눗셈 / 발산 — 구조적으로 성립 불가

```cpp
const double dx = p1.x - p2.x;
const double dy = p1.y - p2.y;
return std::sqrt(dx * dx + dy * dy);
```

**뺄셈·곱셈·덧셈·`sqrt`뿐이다.** 나눗셈도, 역행렬도, 입력 의존 분모도 없다.
`sqrt` 의 정의역 밖(음수) 입력도 불가능하다. — `dx*dx + dy*dy` 는 항상 0 이상이다.

### 2.2 ✅ 오버플로 / 언더플로 — 도메인상 도달 불가

`hypot` → `sqrt` 교체로 포기한 것은 극단값에서의 스케일링 보호다. 이 도메인에서는
도달할 수 없는 영역이다.

| 항목 | 값 |
|------|-----|
| 좌표 범위 | `worldBounds` 안의 미터 값 — \|dx\| 최대 10⁴ 수준 |
| `dx*dx` 최대 | 약 10⁸ |
| `double` 상한 | 1.8 × 10³⁰⁸ |
| **오버플로 여유** | **300 자릿수** |
| 언더플로 임계 | \|dx\| < 1e-154 |
| 최소 유의 임계값 | `dedupMergeDistance` (미터 단위) |

언더플로가 발생하려면 두 객체가 1e-154 m 이내여야 한다. 원자 반지름이 1e-10 m 다.

> **ℹ️ `worldBounds` 미설정 시**: `bounds_.enabled == false` 면 좌표 상한이 강제되지 않는다.
> 그래도 좌표는 카메라 설치 좌표 + 미터 단위 관측값의 합이라 10³⁰⁸ 에 도달할 경로가 없다.
> 오버플로보다 **A1(NaN)** 이 실질적 위험이다.

### 2.3 ⚠️ NaN/Inf 전파 — 이 계층은 막지 않는다 (A1)

```cpp
// 방어 없음 — 의도적
return std::sqrt(dx * dx + dy * dy);   // NaN in -> NaN out
```

비유한 좌표가 들어오면 결과도 비유한이다. **이 계층에 검사를 넣지 않은 것은 의도된
설계 결정**이며, 근거는 4.2(비용이 O(N²)로 증폭됨)와 아래 "올바른 방어 위치"다.

**실측 확인:**

```text
hypot(NaN, ...) = nan
d < 5.0  (warningDistance 판정) = false
d > 5.0  (dedup/track 판정)     = false
-> 두 비교가 모두 false: 경보도 안 나가고 병합도 안 된다 (조용한 실패)
```

NaN은 **모든** 비교 연산에서 false를 반환한다. 결과적으로:

| 호출 지점 | 판정식 | NaN일 때 | 결과 |
|-----------|--------|----------|------|
| `ThresholdRiskPolicy.cpp:49` | `dist < minDist` | false | `nearestGid` 가 0으로 남음 → **차량이 판정에서 통째로 빠짐 → 경보 없음** |
| `ThresholdRiskPolicy` | `minDist <= dangerousDistance_` | false | **Danger 판정 불가** |
| `ConcatFuser.cpp:116` | `dist > dedupMergeDistance_` | false | 병합되지 **않아야** 할 것이 병합 후보로 남음 |
| `GridFuser.cpp:136` | `dist > dedupMergeDistance_` | false | 위와 동일 |

**최악 시나리오**: 카메라 하나가 NaN 좌표를 내면 그 객체와 비교되는 **차량 전체가
위험 판정에서 사라진다.** 컴파일 오류도, 런타임 오류도, 로그도 없다.

#### 상류가 막지 못하는 이유 (확인됨)

`AffineLocalToWorldTransform.cpp:89` 의 범위 검사는 NaN을 통과시킨다.

```cpp
if (bounds_.enabled && (worldX < bounds_.minX || worldX > bounds_.maxX || ...))
```

NaN은 `<` 와 `>` 모두 false이므로 **이 조건 전체가 false가 되어 폐기되지 않는다.**
`bounds_.enabled == false` 면 검사 자체가 없다.

#### 올바른 방어 위치

**변환 계층(O(N))이지 거리 계층(O(N²))이 아니다.**

객체 N개를 변환할 때 검사는 N회지만, 거리 계층에 넣으면 N² 회가 된다. 같은 방어를
**제곱만큼 비싸게** 사는 셈이다.

권고 패치(`AffineLocalToWorldTransform.cpp`, 범위 검사 **앞**):

```cpp
if (!std::isfinite(worldX) || !std::isfinite(worldY)) {
    ++nonFiniteCount_;
    // 기존 outOfBounds 와 동일한 rate-limit 패턴으로 로그
    continue;   // 폐기
}
```

`continue` 가 옳다. 비유한 좌표는 "위치를 모른다"는 뜻이고, 위치를 모르는 객체는
융합에도 위험 판정에도 참여할 수 없다. 남겨 두면 조용히 다른 객체의 판정까지 오염시킨다.

## 3. 메모리 & 스택 안전성

### 3.1 ✅ 힙 할당 0 — OOM 위험 없음

| 저장소 | 형태 |
|--------|------|
| `EuclideanMetric` 멤버 | **없음** (빈 클래스, vtable 포인터만) |
| 함수 지역 | `double` 2개 — **O(1)** |
| 반환값 | `double` (값 반환) |

**동적 자료구조를 소유하지 않는다.** 큐도, 버퍼도, 캐시도 없다. 따라서:

- 호출 횟수와 무관하게 메모리 사용량이 **상수**다
- 소비자가 느리거나 도달 불가여도 **누적될 대상 자체가 없다**
- "metric avalanche" 유형의 OOM은 **구조적으로 성립하지 않는다**

### 3.2 ✅ 스택 오버플로 — 구조적 면역

- **재귀 없음.** `calculate()` 는 분기 없는 단일 표현식이다.
- 지역 저장소는 `double` 2개 — 입력 크기와 무관한 **O(1)**.
- VLA·`alloca`·대형 `std::array` 없음.

### 3.3 ✅ 데이터 경합 — 무상태

`calculate()` 는 `const` 이고 가변 멤버가 없다. `HomographyTransform::toLocal()` 이
`failureCount_` 때문에 스레드 안전하지 않은 것과 대비된다. **다중 스레드 파이프라인으로
확장해도 락 없이 그대로 공유 가능**하다.

이는 A1의 방어를 이 계층에 넣지 **않아야 할** 또 다른 이유이기도 하다. 실패 카운터를
추가하는 순간 무상태 성질이 깨진다.

## 4. 성능 (CPU)

### 4.1 ✅ `hypot` → `sqrt` — O(N²) 경로 5배 단축

| 방식 | N=50 (1,225쌍) | N=200 (19,900쌍) |
|------|----------------|------------------|
| `hypot` (가상 호출) | 7.17 µs | 216.57 µs |
| `sqrt` (가상 호출) | 3.27 µs | **41.93 µs** |
| **개선** | **2.19배** | **5.17배** |

`sqrt` 는 하드웨어 명령 하나, `hypot` 은 libm 함수 호출이다. 호출 지점이 전부 이중 루프
안이라 호출당 수 나노초 차이가 제곱으로 증폭된다.

포기한 것은 극단값 스케일링 보호이며, 2.2에서 보였듯 이 도메인에서는 도달 불가 영역이다.

### 4.2 ⚠️ O(N²) 증폭 — CPU 고갈의 실질 경로

`calculate()` 자체는 저렴하지만 **호출 횟수가 객체 수의 제곱**이다.

| N (윈도우 내 객체) | 쌍 수 | `sqrt` 기준 (x86) | 프레임 예산(100ms) 대비 |
|--------------------|-------|-------------------|-------------------------|
| 50 | 1,225 | 3.3 µs | 0.003% |
| 200 | 19,900 | 41.9 µs | 0.04% |
| 3,072 (이론상 최악) | 4,717,056 | 약 9.9 ms | 9.9% |

이론상 최악은 `channelCount(12) × kMaxObjectsPerFrame(256) = 3,072` 이다. 라즈베리파이
기준 3~5배를 적용하면 **30~50 ms** 로 100 ms 예산의 상당 부분을 먹는다.

**완화 요인:**

- `GridFuser` 를 쓰면 브로드페이즈가 O(N·k) 로 줄어 융합 쪽 호출이 급감한다
  (`ConcatFuser` 는 O(N²) 그대로)
- 집계기의 `kMaxObjectsPerFrame` 상한이 N의 절대 상한을 보장한다
- 현장 전형값은 N ≤ 50

**➡️ 상한이 존재하고 계산 가능하므로 무한 증폭은 없다.** 다만 최악값이 예산의 10%를
차지하므로, 객체 수가 늘어나는 배치에서는 `GridFuser` 선택이 권고 사항이 아니라 요구사항이 된다.

### 4.3 ℹ️ 가상 디스패치 — 제거 이득 없음 (측정됨)

| 방식 | N=50 | N=200 |
|------|------|-------|
| 가상 호출 | 3.27 µs | 41.93 µs |
| 직접 호출 | 2.88 µs | 42.93 µs |

N이 커지면 분기 예측기가 단일 구현을 학습해 간접 호출 비용이 사라진다.
**DI의 교체 가능성을 포기할 이유가 없다.**

### 4.4 ℹ️ 제곱거리 최적화 — 이득 없음 (측정됨)

`sqrt` 를 완전히 제거해도 N=200에서 41.93 → 41.79 µs, **0.3%** 차이다. `sqrt` 는
파이프라인된 단일 명령이라 루프의 나머지 비용에 묻힌다.

인터페이스를 둘로 쪼개고 6개 호출 지점의 임계값을 제곱 도메인으로 옮기는 복잡도를
0.3%와 맞바꾸지 않는다. 임계값 제곱을 빠뜨린 호출 지점 하나가 **조용한 오판정**이 된다는
위험까지 감안하면 순손실이다.

| **A4** | `worldBounds` 미설정 시 좌표 상한 없음 | ℹ️ Info | 2.2에서 보였듯 오버플로 도달 경로는 없다. 다만 `hypot`→`sqrt` 전환의 전제가 `worldBounds` 이므로, 설정을 권고 |

**총평**: `EuclideanMetric` 은 **이 코드베이스에서 가장 단순한 계층**이다. 상태도, 할당도,
I/O도, 로그도 없어 대부분의 위협 범주가 **구조적으로 성립하지 않는다.** 본 감사가 전제했던
지표 파이프라인 위협(블로킹 I/O, 이벤트 큐 폭주, 소비자 정체)은 이 컴포넌트에 해당 구조가
없어 적용 대상이 아니다.

실질적 개선은 두 가지였다. **성능**은 `hypot`→`sqrt` 로 O(N²) 경로를 5.17배 단축했고,
제곱거리·devirtualization 은 측정 결과 이득이 없어 **도입하지 않았다.** — 복잡도만
늘리는 최적화를 측정으로 걸러낸 것도 감사의 결과다.
