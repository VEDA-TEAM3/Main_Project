# Metric 성능 지표 (Before / After)

| 항목 | 값 |
| --- | --- |
| 대상 | `EuclideanMetric` (`IDistanceMetric` 구현) |
| 측정 일자 | 2026-07-30 |
| 측정 방식 | **실측** (추정 아님) — `steady_clock` p50 샘플링 |
| 측정 환경 | x86_64 / WSL2 / g++ `-O2` / 단일 스레드 |
| Before | `std::hypot(dx, dy)` |
| After | `std::sqrt(dx*dx + dy*dy)` |

> **측정 환경 주의**: 라즈베리파이 4(ARM64)가 아니라 x86 개발 장비 수치다.
> 절대값은 Pi에서 3~5배 커지지만 **배율(5.17배)은 하드웨어와 무관하게 유지**된다
> — `sqrt` 는 하드웨어 명령, `hypot` 은 libm 호출이라는 구조적 차이이기 때문이다.
> Pi 실측치는 `performance/control-server.md` 에 별도 갱신 필요.

---

## 측정 조건

| 파라미터 | 값 | 근거 |
| --- | --- | --- |
| N = 50 | 1,225 쌍 | 현장 전형값 (윈도우 내 객체 수) |
| N = 200 | 19,900 쌍 | 혼잡 시나리오 |
| 좌표 분포 | `[-50, 50]` m 균등 | 주차장 도면 규모 |
| 반복 | N=50 → 20,000회 / N=200 → 2,000회 | p50 안정화 |
| 호출 형태 | `IDistanceMetric*` 가상 호출 | 프로덕션과 동일 |

호출 패턴은 `ConcatFuser` 의 이중 루프를 그대로 재현했다 (`i < j` 전체 쌍).

## 1. 핵심 성과 — `hypot` → `sqrt`

| N | Before (`hypot`) | After (`sqrt`) | 개선 |
| --- | --- | --- | --- |
| 50 (1,225쌍) | 7.17 µs | **3.27 µs** | **2.19배** |
| 200 (19,900쌍) | 216.57 µs | **41.93 µs** | **5.17배** |

쌍당 비용:

| N | Before | After |
| --- | --- | --- |
| 50 | 5.9 ns/쌍 | 2.7 ns/쌍 |
| 200 | 10.9 ns/쌍 | 2.1 ns/쌍 |

> N이 커질수록 배율이 커지는 이유: `hypot` 은 호출당 고정 비용(함수 호출 + 스케일링 분기)이
> 크고 캐시·파이프라인 친화적이지 않다. `sqrt` 는 파이프라인되어 반복 횟수가 늘수록
> 쌍당 비용이 오히려 **내려간다** (2.7 → 2.1 ns).

### 포기한 것

`hypot` 의 극단값 스케일링 보호. `dx*dx` 가 `double` 범위를 넘거나 언더플로하는 경우에도
정확한 결과를 보장하는 기능이다.

| 항목 | 값 |
| --- | --- |
| 좌표 범위 (`worldBounds`) | 미터 단위, \|dx\| 최대 10⁴ 수준 |
| `dx*dx` 최대 | 약 10⁸ |
| `double` 상한 | 1.8 × 10³⁰⁸ |
| **오버플로 여유** | **300 자릿수** |
| 언더플로 임계 | \|dx\| < 1e-154 (원자 반지름 = 1e-10 m) |

**도달 불가능한 영역의 보호를 O(N²) 경로 전체의 5배 비용과 맞바꾸고 있었다.**

## 2. 프레임 예산 대비

윈도우 100 ms 기준. 거리 계산만의 비용이다.

| N | 쌍 수 | After (x86) | 예산 대비 | Pi 추정 (×4) | Pi 예산 대비 |
| --- | --- | --- | --- | --- | --- |
| 50 | 1,225 | 3.3 µs | 0.003% | 13 µs | 0.013% |
| 200 | 19,900 | 41.9 µs | 0.04% | 168 µs | 0.17% |
| 3,072 (이론상 최악) | 4,717,056 | 9.9 ms | 9.9% | 40 ms | **40%** |

이론상 최악은 `channelCount(12) × kMaxObjectsPerFrame(256) = 3,072` 이다.

**Before 기준으로 같은 최악값을 계산하면 x86에서 51 ms, Pi에서 200 ms 로 프레임 예산을
통째로 초과한다.** 이 패치는 최악 시나리오에서 예산 초과를 예산 40%로 되돌린다.

> 상한이 존재하는 것은 집계기의 `kMaxObjectsPerFrame` 덕분이다. 그 상한이 없으면
> 이 표에 최악값 자체가 존재하지 않는다.

## 3. 도입하지 않은 최적화 (측정으로 기각)

### 3.1 제곱거리 비교 — 이득 0.3%

호출 지점 6곳 중 4곳이 임계값 비교만 한다(`dist > threshold`). 이론적으로 `sqrt` 를
완전히 제거할 수 있다.

| 방식 | N=200 |
| --- | --- |
| `sqrt` (가상 호출) | 41.93 µs |
| 제곱거리 (직접, `sqrt` 없음) | 41.79 µs |
| **차이** | **0.3%** |

**기각.** `sqrt` 는 파이프라인된 단일 명령이라 제거해도 루프의 나머지 비용에 묻힌다.
인터페이스를 둘로 쪼개고 6개 호출 지점의 임계값을 제곱 도메인으로 옮기는 복잡도를
0.3%와 맞바꾸지 않는다. 임계값 제곱을 빠뜨린 호출 지점 하나가 **조용한 오판정**이 된다.

### 3.2 가상 디스패치 제거 — 이득 없음

| 방식 | N=50 | N=200 |
| --- | --- | --- |
| 가상 호출 | 3.27 µs | 41.93 µs |
| 직접 호출 | 2.88 µs | 42.93 µs |
| 차이 | 1.14배 | **없음** |

**기각.** N이 커지면 분기 예측기가 단일 구현을 학습해 간접 호출 비용이 사라진다.
N=200에서는 직접 호출이 오히려 느리게 측정됐다(측정 잡음 범위). DI의 교체 가능성을
포기할 이유가 없다.

## 4. 할당 / 메모리

| 지표 | Before | After |
| --- | --- | --- |
| 호출당 힙 할당 | 0 | 0 |
| 상주 메모리 | vtable 포인터만 | 동일 |
| 상태 | 없음 (`const`) | 동일 |

**이 계층은 리팩터 전에도 무할당·무상태였다.** 개선 여지가 없었고 변경도 없다.
동적 자료구조를 소유하지 않으므로 호출 횟수와 무관하게 메모리 사용량이 상수다.

## 6. 회귀 감시

이 계층에는 런타임 지표가 없다(무상태 순수 함수). 회귀는 코드 리뷰로만 잡힌다.

| 회귀 | 증상 | 탐지 |
| --- | --- | --- |
| `hypot` 으로 되돌림 | O(N²) 경로 5배 저하 | 런타임 지표 없음 — **리뷰에서만 잡힘** |
| 제곱거리 도입 시 임계값 제곱 누락 | 조용한 오판정 (경보 민감도 변화) | 없음 |
| 거리 정의 교체 시 임계값 미조정 | 경보 민감도 변화 | 없음 |

> **⚠️ 이 계층의 성능 회귀는 지표에 나타나지 않는다.** 상위 컴포넌트(`ConcatFuser`,
> `ThresholdRiskPolicy`)에도 거리 계산만 분리한 카운터가 없다. 회귀를 잡으려면
> `tests/` 에 벤치마크를 등록하는 것이 유일한 자동 수단이며, control-server가 테스트
> 범위에 들어올 때 함께 검토한다.
